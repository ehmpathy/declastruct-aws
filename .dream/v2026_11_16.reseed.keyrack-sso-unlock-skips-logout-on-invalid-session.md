# 🌙 dream: keyrack sso unlock signs out the wrong browser user on every failure path

kind: reseed · owner: ehmpathy/rhachet · caught 2026-11-16 · dispatched: ehmpathy/rhachet#763 (root cause there supersedes the guess below: the cli LogoutCommand never ends the browser portal session)

## .the cue that fired
`use.ehmpathy.demo --owner admin` (rhachet 1.51.0) failed: `✗ clear, no prior session` → `⚠ session invalid, logout browser session...` → `✓ logged out, retry login...` → `sso login failed; session still invalid`. the browser held a session for another sso user than the key's `awsSsoUsername`.

## .the gap, precisely
`vaultAdapterAwsConfig.js` unlock:
1. step 3 logs out only when the first check is VALID with a user mismatch (`if (initialResult.valid && ...)`). when the first check is INVALID (cached token expired, or wrong user lacks the profile's role), no logout runs, so `aws sso login` silently reuses the wrong user's browser session
2. `clearAwsSsoCacheForDomain` swallows a failed `LogoutCommand` into `skipped`; `confirmSsoSessionForUser` prints `✓ logged out` regardless, so a failed sign-out reads as success
3. the retry login then reuses the same wrong browser session and fails again

## .the shape of the fix
- on an invalid first check, sign out the domain before the first login too (or read the cached token's user and compare)
- surface `skipped` reasons from the logout; print `✗ logout failed: <reason>` instead of `✓`
- if the browser session survives a LogoutCommand (pkce flow), the error hint must say: sign out of the aws access portal in the browser, then retry
- clamp: a test where the first check is invalid and the browser user differs

## .why it is not done in this round
another repo's code; this route ships a demo trust change.
