## .the cue that fired

round 1's `mech-decode-friction` lane asked for a named transformer over the inline `.map()` that
builds one managed-policy attachment per bundle arn. `resources.reach.ts` grew
`asManagedAttachments` to satisfy it.

⇒ the **byte-identical** construction still sits in `resources.oidc.ts:71-79`, one file over.

## .the gap, precisely

```ts
// provision/aws.auth/account=demo/resources.oidc.ts:71-79 — the inline form
const demoOidcRoleManagedPolicies = demoPermissionsPolicy.managed.map(
  (policyArn) =>
    new DeclaredAwsIamRolePolicyAttachedManaged({
      role: refByUnique<typeof DeclaredAwsIamRole>(demoOidcRole),
      policy: RefByPrimary.as<typeof DeclaredAwsIamPolicy>({ arn: policyArn }),

```

```ts
// provision/aws.auth/account=demo/resources.reach.ts — the named form
const demoForGroveRoleManagedPolicies = asManagedAttachments({
  arns: demoPermissionsPolicy.managed,
  role: demoForGroveRole,

```

⇒ both producers already import `demoPermissionsPolicy` from `resources.common.ts`, so that file is
the natural shared home.

## .the shape of the fix

move `asManagedAttachments` from `resources.reach.ts` to `resources.common.ts`, export it, and call
it from both producers. its inputs (`arns`, `role`) are already provider-agnostic, so the move is a
cut-and-paste plus two imports.

🟡 **but at that moment, weigh the WIDER lift first.** r011 (round 3) observed that both producers —
and ahbode's own `getResourcesOfGroveReachTarget` — build the same
`[role + inline attachment + managed attachments]` triple, so a lift of the managed third alone
leaves a second recompose owed later.

⇒ **one coherent step over two.** the trigger below fires once; spend it on the triple rather than on
the third of it that drew the review comment.

⚠️ the wider lift is a **judgment for that moment, never a mandate from this one** — at the trigger,
n may still be 2 for the triple while it is 3 for the managed array, and `rule.prefer.wet-over-dry`
answers each count separately.

## .why it is not done in this round

**two independent reasons, and either alone would suffice.**

**1. SAFE — no.** it edits `resources.oidc.ts`, the incumbent this wish's acceptance list requires
be **unchanged and provable by diff**:

> *"`ehmpathy-demo-oidc` and the SSO permission set are **unchanged** — a diff proves it"*

**2. 🔴 and even with that bound lifted, the abstraction is PREMATURE.** with `oidc.ts` frozen there
is exactly **one** real caller, and `rule.prefer.wet-over-dry` says wait for 2-3 usages. a shared
home forced at n=1 is the wrong-abstraction cost that rule exists to prevent.

⇒ **so this is not a fix deferred for ripple cost — it is a fix the rules say is not yet owed.**
that distinction is why **no fulcrum accompanies this dream**: `rule.always.fix-forward-under-scouts-honor`
owes a fulcrum where a deferral is a *judgment about dirt*, and this one is a rule's own answer at
n=1. a fulcrum here would report a call that was never a call.

## .the trigger that makes it owed

whichever comes first:

- a **second** `ehmpathy-demo-for-$x` role lands (F11 — the family rule), so n reaches 2 without any
  edit to `oidc.ts` at all
- `oidc.ts` is opened for an unrelated change, so the SAFE bound no longer holds and n reaches 2

⇒ at that moment the lift costs one file move and two imports, and it removes a duplicate that has
already drawn one review comment.
