# 🌙 dream: one shared keyrack-creds operation for this repo's aws skills

kind: fix · owner: declastruct-aws maintainers · caught 2026-11-15

## .the cue that fired

a peer review (`enroll-impl-arch-defects`, i004 nitpick.3) counted the keyrack unlock + source block in eleven skills under `.agent/repo=.this/role=any/skills/`. `aws.auth.demo.plan.sh` is the eleventh, and the only one that hardens it.

## .the gap, precisely

- ten skills (`report.cost*`, `use.ssh.tunnel`, `aws.ssm.sessions`, `aws.ssh.config`, `mail.dns.*`, `echo.*`) each carry their own copy of the unlock + `keyrack source` block
- none of the ten unsets ambient `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN` / `AWS_PROFILE` before the source, so an ambient profile can leak into them
- none of the ten proves the creds with `sts get-caller-identity` before the first read

## .the shape of the fix

- one `keyrack.creds.operations.sh` beside the skills, sourced by each: `ensure_creds env=<env>` that unlocks, unsets every ambient `AWS_*` by prefix (`for v in "${!AWS_@}"; do unset "$v"; done`, so `AWS_CONFIG_FILE`, `AWS_ENDPOINT_URL`, and kin go too), sources `AWS_PROFILE`, fails loud on absent or unauthenticated creds (exit 2, qualified headers)
- move each of the eleven onto it; each skill's own tests stay green
- one test of the operation through fakes on PATH, as `aws.auth.demo.plan.integration.test.ts` does

## .why it is not done in this round

it touches ten skills unrelated to the grove trust fix; that rewrite would leave this pr's scope (trust-only) and fail CLEAN.
