# vision — -for-grove trust admits roles anywhere sessions

## the outcome world

a clone on the hetzner grove signs in through iam roles anywhere, hops into demo as `ehmpathy-demo-for-grove`, and works. today that hop dies at sts with `AccessDenied` on `sts:SetSourceIdentity`.

| | before | after |
|---|---|---|
| trust `action` | `sts:AssumeRole` | `[sts:AssumeRole, sts:TagSession, sts:SetSourceIdentity]` |
| trust `principal` | the camp grove role | unchanged |
| hetzner (roles anywhere) hop | ⛔ AccessDenied | ✅ |
| ec2 (imds) hop | ✅ | ✅ |
| any other principal | ⛔ | ⛔ |
| demo plan | — | one `UPDATE` on the role, trust action only; all else `KEEP` |

the aha: a roles anywhere session is born with a source identity and principal tags from its cert. the source identity persists through every role chain (aws docs); the tags follow it too (measured live, issue #129). the target trust must say yes to both, or sts says no to the whole hop. the ec2 grove never hit it because its session carries neither.

## the contract

one edit to the one trust statement in `provision/aws.auth/account=demo/resources.reach.ts`:

```ts
new DeclaredAwsIamPolicyStatement({
  effect: 'Allow',
  principal: { aws: campGroveRoleArn },
  action: ['sts:AssumeRole', 'sts:TagSession', 'sts:SetSourceIdentity'],
}),
```

the pins that move with it:
- `resources.reach.test.ts` [t0] `grants sts:AssumeRole, and only it` → grants exactly these three
- `resources.reach.integration.test.ts` [t5] → the live trust holds exactly these three
- `__snapshots__/resources.reach.test.ts.snap` [t4] → expected to hold: the role row's identity keys on `name` alone (`src/domain.objects/DeclaredAwsIamRole.ts:69`), and the trust is not part of it

one doc row moves with it: `readme.reach.md`'s AccessDenied table gains a cause — a roles anywhere session meets a target trust that lacks `sts:SetSourceIdentity` / `sts:TagSession`; the error names the action, and the fix is this trust shape. the next `-for-$x` or prep role then fails with a known cause, not a fifth mystery. this row goes beyond the wish's letter; it adds no plan row, and is cuttable at the commander's word.

the apply follows `provision/aws.auth/account=demo/readme.md`, on the commander's go, never before.

## mental model

"the grove's badge now shows its name tag at the door." the role always let the grove in; it just refused guests who wore a name tag and a lanyard. roles anywhere guests always wear both.

| commander says | code says |
|---|---|
| roles anywhere session | a session with a source identity + principal tags |
| the trust | `DeclaredAwsIamRole.policies[0]` |
| one-line trust change | `action` scalar → array of three |

## evaluation

- solves the goal: yes, for test. the hop's two measured denials map one-to-one to the two added actions
- pros: one field, one role; no principal change; ec2 grove untouched; cicd untouched
- cons: prep is not declared in this repo (open question 2)
- edge: `TagSession` + `SetSourceIdentity` also let the camp grove role **set** tags or a source identity on a fresh hop. that admits no new principal, and grants no new permission through any declared policy: none in `ehmpathy/*` keys on principal tags (open question 7)
- edge: iam is eventually consistent. a hop proof run seconds after the apply may still deny; one retry is the fallback (case=6)
- edge: a revoke rewrites the whole statement (`howto.revoke-grove-reach`), so the extra actions die with it
- pit of success: the plan read is the guard. any row beyond one trust-action `UPDATE` is a STOP (case=2)

## groundwork

### external

- aws iam, *monitor and control actions taken with assumed roles* (`docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_temp_control-access_monitor.html`): a set source identity persists across role chains; cross-account, the target's trust must allow `sts:SetSourceIdentity` or the assume fails
- aws roles anywhere, *trust model* (`docs.aws.amazon.com/rolesanywhere/latest/userguide/trust-model.html`): sessions carry source identity = cert subject cn, and principal tags from subject/issuer/san; trust examples allow `sts:AssumeRole`, `sts:TagSession`, `sts:SetSourceIdentity`
- issue `ehmpathy/declastruct-aws#129`: measured AccessDenied on SetSourceIdentity, then TagSession; caller half applied; proof command `rhx grove.reach.hop.prove`

### internal

- `provision/aws.auth/account=demo/resources.reach.ts:247` — the one trust statement, `action: 'sts:AssumeRole'`
- `src/domain.objects/DeclaredAwsIamPolicyStatement.ts:44` — `action: string | string[] | DeclaredAwsIamStatementScope`; arrays supported (`.test.ts` case5)
- `provision/aws.auth/account=demo/resources.reach.test.ts:143-146` — pins the scalar
- `provision/aws.auth/account=demo/resources.reach.integration.test.ts:190-194` — pins `['sts:AssumeRole']` live
- `src/domain.operations/iamRole/setIamRole.ts:58-105` — an upsert on an extant role sends `UpdateAssumeRolePolicy` with the WHOLE trust document, and touches description or tags only where they differ. so the apply writes the trust alone, and it rewrites the principal from `.env` each time: the plan's principal read (case=2) carries real weight
- `node_modules/declastruct/dist/domain.operations/apply/applyChanges.js` (declastruct 1.7.3) — apply re-plans, then `assertPlanStillValid` refuses if the fresh plan differs from the plan file. so the go applies exactly what was read, and `.env` must still be sourced at apply (the runbook's one-shell rule)
- `provision/aws.auth/account=demo/readme.md` — the apply runbook + plan checks
- `provision/aws.auth/resources.common.roundtrip.test.ts` — array actions already round-trip in the shared bundle
- org search `for-grove` across `ehmpathy/*`: one declared role, this one

- the wish's title names one action; the measured fix needs two
