# case=8 — an actionless lifecycle object is rejected, and names `lifecycle: null`

**feel** sharp · **care** critipath · **actor** `consumer` · **cells** invariant I-6

⚠️ **added by the `has-experience-coverage` self-review.** I-6 was graded *"itemized, sharp, criti
**if it throws**"* — a conditional that made the grade hostage to an unverified aws answer (Q-9).
the **guard**, though, never depended on that answer, and once review 1's defect 28 surfaced the
remedy the conditional had no work left to do.

**this wish creates the shape.** it is unreachable in `1.11.0` and readily written in `1.12.0`.

## .narrative

kai declares a bucket. he does not want any lifecycle behaviour on it — no transitions, no expiry,
no cleanup. he starts to write the field and the compiler will not let him leave it alone:

```ts
lifecycle: {
  objects:    { expire: null, transitions: [] },    // no expiry, no class moves
  versions:   false,                                // no version history
  multiparts: { expire: null },                     // no cleanup
},
```

each `null` is typed out because `rule.forbid.undefined-inputs` bars an optional field. he has
answered every question the type asked, honestly, and the object he produced **declares no action at
all**.

### 🔴 why this shape is new, and why it is now easy to write

in `1.11.0` the lifecycle carried **two** fields, and an author who wanted no behaviour wrote
`lifecycle: null` because the object had an obvious emptiness. this wish takes it to **four** — and
the more values a type demands, the more natural it feels to satisfy them all with `null` rather than
to step back and null the parent. **`rule.forbid.undefined-inputs` is what makes the shape
reachable**; it is a pit-of-success rule that, here, paves a path to an object with no content.

### 🔴 F16 made the empty object HARDER to see, and that is a cost against the F16 call

the flat form read, visibly, as **a form filled with blanks** — four `null`s in a column, and the
emptiness was the shape on the page. the nested form reads as **three tidy declarations**, and one of
them is not blank at all: `versions: false` is an affirmative statement about a real state.

⇒ so an author who scans their own diff sees an object that looks **more** considered while it
declares exactly as little. 🔴 **F16 improved every legibility property this vision measured and
degraded this one** — and it degraded precisely the property this case's edge turns on. that is
recorded against **F16** as a cost the call carries, and it is the argument for why the guard is
**not** optional under the new shape: what a reader could once catch by eye now needs a machine.

and `setS3Bucket.ts:54` branches on a **truthy** test:

```ts
if (desired.lifecycle) {          // ← an all-empty object is TRUTHY
  await putBucketLifecycle({ … });
}
```

so kai's object is sent to aws as a real rule, with `Transitions: []` and no action sub-objects at
all — a wire shape this package has never produced.

### what he wanted, and the word for it

the dobj already has a name for his intent, and it is not this object.
`DeclaredAwsS3BucketLifecycle.ts:9` defines the modes, and the first one is his:

> *"**persist** — a **null** lifecycle on the bucket (no rule at all)"*

⇒ **`lifecycle: null` is the documented idiom for "no lifecycle".** kai wrote four nulls where the
shape's own contract asked for one, and the type did not stop him.

## .the fail-safe

the guard is a construction-time rejection that names the idiom:

```
BadRequestError: lifecycle declares no action

  why: objects.transitions is empty, every expire is null, and versions is false —
       so this rule would ask aws to do no work. the shape's own contract calls
       that the `persist` mode, and spells it as an absent lifecycle — not an
       empty one.

  fix: lifecycle: null
```

🔴 **F16 changed the predicate's shape, and the `why` line has to follow it.** under the flat form
the check was *"transitions empty **and** three nulls"* — one array and three scalars, all peers.
under F16 the guard must read **`versions: false` as an emptiness too**, and `false` is not `null`:
it does not fall out of a generic `Object.values(…).every(v => v === null)` sweep. ⇒ **the guard
walks the three keys by name, never by a null-sweep.**

### 🔴 and F16 broke the FIX line in one cell — the one the guard must not reach

`lifecycle` now carries a key that is **not** part of the lifecycle rule at all. `versions.status`
is written by `PutBucketVersioning`; only `versions.expire` reaches
`PutBucketLifecycleConfiguration` (F16 sub-call 2). so consider:

```ts
lifecycle: {
  objects:    { expire: null, transitions: [] },
  versions:   { status: 'suspended', expire: null },   // ← a REAL declaration
  multiparts: { expire: null },
},
```

**every value here is inert as a lifecycle rule** — aws would be asked for no lifecycle work at all.
so a guard written as *"reject when the rule would carry no action"* fires. and its `fix: lifecycle:
null` would tell the consumer to **delete a `suspended` declaration they meant**, which is a retract
of a real state dressed as a tidy-up.

⇒ **the guard's subject must be the lifecycle RULE, and its trigger must be the whole `lifecycle`
FIELD, and F16 made those two things different.** the predicate that stays honest is:

> reject when `objects.expire` is null **and** `objects.transitions` is empty **and**
> `multiparts.expire` is null **and** `versions` is exactly `false`.

the fourth term is `=== false`, **not** *"has no expiry"* — a `versions` object always declares a
state worth keeping, whatever its expiry says. ⚠️ **that asymmetry is invisible in the flat shape's
guard and is the single easiest way to implement this case wrongly under F16.** it is owed a
`[t3b]` step below and a criterion at `2.1.criteria`.

🟢 its content was **RULED IN 2026-09-09 (F8 confirmed)**, as case=3, 4, 6 and 7 were; only the
carrier half of Q-7 stayed unasked. `BadRequestError` is the class —
verified available from `helpful-errors` and used by this repo's own caller-rejection precedent,
`assertPredictionIntervalValid.ts`, which extracts the check as *"a pure guard … so its fail-loud
path is unit-testable without a live read"*. that is the shape to copy: a pure `assert*` guard, not
a branch buried in the set.

### 🔴 the guard does NOT depend on Q-9, which is why it is writable now

| aws's answer to Q-9 | what changes |
|---------------------|--------------|
| aws **rejects** an actionless rule | the guard turns a deep, late `MalformedXML`-class api error into a near, legible one that names the fix |
| aws **accepts** it | the guard turns a silent no-op rule — one that occupies the bucket's single declastruct-owned rule slot and does no work — into a legible rejection |

⇒ **both branches want the same guard**, so it is implementable before the live call. that is the
whole reason the *"criti if it throws"* conditional is retired: the conditional graded the
**hazard**, and the hazard's remedy was never conditional.

⚠️ Q-9 still stands as an execution obligation — the *other* half of it (does aws accept
`Transitions: []` beside only the two new sub-objects, which is **case=1's exact wire shape**) is a
separate and live question this guard does not answer.

### the fail-safe grade — **all five clauses**, at the edge

🔴 **added at verified21.** peer review r2 (verified15, nitpick.3) graded this gap on **c6**; the
sibling check found it on **four** cases — c3, c6, c7, c8. ⚠️ **c8 is the one where the grade is
almost entirely green, and that is itself the find**: it is the cheapest fail-safe in the wish, and
the table is what lets a reader see that at a glance rather than infer it from prose.

| # | clause | grade |
|---|--------|-------|
| 1 | **fast** | ✅ **the earliest edge in the whole wish — CONSTRUCTION time.** it fires before plan, before apply, before any aws call whatsoever. no other case in this vision fails this early |
| 2 | **loud** | ✅ `BadRequestError` — the caller-rejection class, thrown from a pure `assert*` guard, never a silent no-op rule |
| 3 | **teaches the fix** | ✅ **and it teaches a fix that is exactly one token**: `lifecycle: null`. it is not a hint or a direction — it is the literal replacement text, and it is the idiom the shape's own contract already defines as the `persist` mode. 🟢 content **ruled in** by F8, 2026-09-09; only the carrier stayed unasked |
| 4 | **holds the limit** | ✅ the limit is *a rule must carry at least one action*. the guard holds at it. the overshoot it bars is subtle and worth a name: an actionless rule would consume the bucket's **single declastruct-owned rule slot** and do no work — so a later real rule would silently have no room |
| 5 | **drops no data silently** | ✅ **vacuously and permanently.** the rejection precedes every aws call, so no bucket, no rule, and no object is touched. this clause cannot be at risk at a construction-time edge — which is the structural reason rung-1 guards are preferred |

⇒ 🔴 **five clauses, five passes, at a cost of one pure guard with no live dependency** — the
`.the guard does NOT depend on Q-9` section above is what makes that true. ⚠️ **the contrast with c7
is the useful one**: both are sharp critipaths whose hazard is a shape a consumer can type, and c8
catches it at construction while c7 cannot catch its own until teardown. *the difference is not
effort — it is whether the hazard is expressible in the type surface at all.*

## .the `[tn]` timeline

```
given  [case8] a consumer who wants no lifecycle behaviour on a bucket
  and  a lifecycle type whose three sub-objects are all required

  when [t0] they declare objects empty, versions false, multiparts.expire null
  then  the object is TRUTHY, so `setS3Bucket`'s `if (desired.lifecycle)` takes the write path
   and  ⚠️ without the guard, `putBucketLifecycle` sends a rule with no actions at all

  when [t1] the guard runs at construction
  then  it rejects with BadRequestError before any s3 call is issued
   and  the message names `lifecycle: null` as the fix
   and  it cites the `persist` mode by name, so the fix is discoverable in the type's own doc

  when [t2] they take the fix and declare lifecycle: null
  then  plan reads the bucket
   and  `delBucketLifecycle` converges an extant rule to absent
        (the same retract path lifecycle/tags/policy already use)
   and  the re-plan reads KEEP

  when [t3] a lifecycle carries empty objects but at least ONE non-null expire
  then  the guard does NOT fire — the rule has an action
   and  ⚠️ this is case=1's backup store, and it MUST remain legal

  when [t3b] a lifecycle is inert as a RULE but carries versions: { status, expire: null }
  then  🔴 the guard does NOT fire
   and  it does NOT advise `lifecycle: null`, which would retract a declared
        version state the consumer meant  (F16 sub-call 2 — `versions.status`
        is written by PutBucketVersioning, never by the lifecycle put)
   and  the predicate's fourth term is `versions === false`, NEVER
        "versions has no expiry"
```

### what the timeline catches that the narrative does not

- **`[t0]`'s truthiness** — the narrative shows an empty-looking object. it cannot show that
  javascript considers it full. `{}` is truthy, so *"no lifecycle"* and *"a lifecycle that declares
  no action"* take **opposite branches** at `setS3Bucket.ts:54` while they read identically on the
  page.
- **`[t1]`'s "before any s3 call"** — a guard that fires after the put has already changed the
  bucket. the whole value is that it is a pure, near rejection.
- 🔴 **`[t3]` is the step that keeps the guard honest.** the obvious over-broad implementation —
  *"reject a lifecycle with no transitions"* — would reject **case=1's backup store**, which
  declares `objects.transitions: []` deliberately and puts all its content in the two new sub-rules.
  the predicate is *"no transitions **and** no expiries"*, never *"no transitions"*. prose would
  never surface that; a step does.
- 🔴 **`[t3b]` is the same lesson one turn further, and F16 is what put it there.** `[t3]` guards
  against a predicate that is too **broad**; `[t3b]` guards against a *fix line* that is too broad —
  a guard can be perfectly correct about "this rule does no work" and still give advice that
  destroys a declaration. ⇒ **F16 split `lifecycle` from "the lifecycle rule", and a guard that
  conflates the two is correct in its trigger and wrong in its remedy.** the narrative cannot
  surface it: kai's story ends with a bucket that works either way.

## .the counterfactual — why an unverified hazard is still a critipath

- **frequency** — it sits on the most ordinary path there is: a consumer who wants **no** lifecycle
  behaviour, faced with four fields the compiler forces them to answer. the wish's own field count
  is what makes the wrong answer the natural one.
- **cost** — it is either a deep api error whose message points at xml rather than at the wish
  (if aws rejects), or a silent no-op rule that consumes the bucket's one declastruct-owned rule
  slot forever (if aws accepts). the second is worse and quieter.

⇒ and the asymmetry that settles the grade: **the guard costs one pure function and one unit test.**
a critipath whose fail-safe is that cheap and that certain has no case for deferral.
