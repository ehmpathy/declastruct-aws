**the latent axis.** this case exists because the decomposition surfaced the eventual-consistency

## .narrative

vlad applies the backup store from case=1 in ci. the apply reports success. the pipeline's very
next step re-plans to assert convergence, and it reads:

```
○ ahbode-camp-git-backup
   ├─ ✔ done in 0.41s
   └─ decision [UPDATE]
      - Remote
      + Desired

        "lifecycle": Object {
          "versions": Object {
      -     "expire": null,
      +     "expire": Object { "after": Object { "days": 30 }, "keep": null },
          },
          "multiparts": Object {
      -     "expire": null,
      +     "expire": Object { "days": 7 },
          },
        }
```

he re-runs it by hand two minutes later. **KEEP.** he re-runs the pipeline. **KEEP.** he cannot
reproduce it. he shrugs and marks the pipeline flaky.

that shrug is the failure. it is not flake — it is aws's read-after-write window, and it will fire
again on the next fresh bucket, in ci, at the worst moment.

## .why the extant guard does not cover it

`setS3Bucket.ts:66-84` already knows this window exists. it polls until the lifecycle config reads
back stably, with a comment that a single matched read *"can regress to null on the very next
read"*. good instinct. but the predicate is:

```ts
stableReads =
  live?.transitions.length === desired.lifecycle.transitions.length
    ? stableReads + 1
    : 0;
```

it compares **only the transition count**. a backup store declares:

```ts
lifecycle: {
  objects:    { expire: null, transitions: [] },            // zero transitions
  versions:   { status: 'enabled', expire: { after: { days: 30 }, keep: null } },  // the real content
  multiparts: { expire: { days: 7 } },                      // …and here
},
```

`live` is `null` while no rule exists, so `live?.transitions.length` is `undefined`, which does
**not** equal `0` — so the loop does wait. but the moment the rule appears with *either* expiry
written, `transitions.length === 0 === 0` matches, and the poll declares stability **without a
single look at the two fields that are the entire point of the write.**

the guard was written for a config whose content lived in `transitions`. this wish moves content
somewhere the guard does not look.

🔴 **F16 widened the repair and made its shape harder to get right.** the flat shape asked the
predicate to compare four peer scalars — a mechanical change a reviewer could eyeball. under F16 it
must walk **three sub-objects whose shapes disagree**: `objects` (a nullable expiry plus an array),
`versions` (a `false` token **or** a two-key object), `multiparts` (one nullable expiry). ⇒ **the
natural implementation is now a deep compare of the whole `lifecycle` object**, and that is both the
correct answer and one the extant `transitions.length` habit actively steers away from. ⚠️ a deep
compare must also be **canonical** — `objects.transitions: []` and an omitted array are one state
with two written forms, and a raw `serialize` compare on them is a permadrift (F11's canonicalizer
obligation, now owed at three nested sites rather than one flat one).

🔴 **but the guard was already blind before this wish touched it** — added by the
`has-questioned-requirements` self-review, which found the sentence above understates its own case.
substitute the **extant** object expiry (`30 → 60`, today's `expireAfterDays`, F16's
`objects.expire`) for the new sub-rule in `[t5]` below and the
predicate is equally blind: `transitions.length` is unchanged on both sides, so the stale pre-put
rule satisfies it outright. ⇒ **every consumer today with a zero-transition or unchanged-transition
lifecycle is already unprotected, on shipped code.** this wish does not create the defect; it
promotes it from a rare case to the **common** one, since a backup store's entire content lives
where the predicate does not look. that is the argument for F6, and it is stronger than the
scope-creep frame the yield used.

## .the fail-safe — graded against the five clauses

the fix is not a new mechanism — it is a **widened predicate**. the stability check must compare
the whole declastruct-owned rule against desired, not one array's length:

| # | clause | c5's proof |
|---|--------|-----------|
| 1 | **fast** | the poll is inside `setS3Bucket`, before the read-back returns. the stale value never leaves the set op (`rule.require.failfast`) |
| 2 | **loud** | the poll has a deadline. on expiry it must **throw**, never return the stale object with a shrug — a silent timeout is the failhide that produces the phantom UPDATE (`rule.forbid.failhide`) |
| 3 | **teaches the fix** | the timeout error names the bucket, the desired config, and the last-read config, so the diff is in the log rather than in a console tab |
| 4 | 🔴 **holds the limit** | **live here, unlike at c4's cell.** the limit is the poll's own **deadline**, and it is two-sided: too short and a legal-but-slow aws converges into a spurious throw; unbounded and the timeout stops to exist, which retires clause 2 with it. ⇒ the deadline is a **declared** number with a stated reason, never an incidental `while` — and the second window (`[t6]`, `[t7]`) needs its **own** number, since aws's documented versioning window is a different order of magnitude from the lifecycle one |
| 5 | 🔴 **drops no data silently** | ✅ **this is the clause c5 exists to prove, and it was the one left ungraded.** the poll's whole subject is a **stale read** — a value that is wrong and reads as right. the obligation is that the broken handoff between write and read-back is **loud**: the stale object never returns, the timeout throws, and the caller therefore never persists a read that s3 has already superseded. ⚠️ a poll that returned the stale value on expiry would drop the write's effect **silently, in the direction that reads as safe** — the apply reports success, the plan reads UPDATE forever, and no error is ever emitted |

🔴 **⚠️ this table graded three clauses until peer review r2.** the omission is the diagnostic part:
the census's clause-5 tally listed three instances and **c5 was not among them** — the one case in the
set whose entire edge **is** a quiet-stale-data hazard was the one case the quiet-data clause skipped.

⇒ **the cause was the shape of the section, not a lapse of care.** the table was headed `| obligation
| how |` and held whichever obligations the case had already reasoned about, so it read as complete at
three. a table headed `| # | clause |` and numbered 1..5 cannot: an absent row is visibly absent. ⇒
*the same lesson as `an ungraded clause and an inapplicable clause are different verdicts` — here
caught one level up, in the FORM that made the ungraded clause invisible.*

## .the SECOND window — cells 1, 2, 3, and why its poll must not copy this one's shape

aws documents a propagation window for `PutBucketVersioning` (fetched and quoted in the yield's
external research — it is what falsified **A-2**). so the three versioning cells carry the same
class of hazard as 14/20: **the write lands, the read lags, the caller re-plans and sees UPDATE.**

⚠️ **but the two polls are not the same poll, and the difference is the whole lesson of this case.**

| | the lifecycle poll (cells 14, 20) | the versioning poll (cells 1, 2, 3) |
|---|---|---|
| what it compares | 🔴 a **proxy** — `transitions.length` | the **value** — `Status` itself |
| why that matters | a proxy can be identical on both sides while the content differs → the blindness above | a scalar has no proxy to reach for; the check is the value or it is no check |
| the absent read | an omitted sub-object → `null` — **indistinguishable** from "not yet" | an empty body → 🔴 **`false`** under F16 — a token, no longer the same value as "absent expiry" |
| is the ambiguity reachable? | ⚠️ **yes** — a `null` expiry is a declarable desired state | ✅ **no** — `versions: false` issues **no call at all** (I-1: there is no retract), so the poll only ever waits for a target that is an **object** |

⇒ **the versioning poll is structurally safer, and only because its target can never be the ambiguous
value.** that is a property to state rather than to rely on silently: an implementer who "reuses the
lifecycle poll shape" inherits the proxy habit, and an implementer who reuses the *versioning* shape
on a nullable property inherits an ambiguity the versioning case never had to face.

🟢 **F16 strengthened the right-hand column, and by construction rather than by care.** under the
flat shape both polls' absent-reads were spelled `null`, so the claim *"ours can never be the
ambiguous value"* rested on a **reachability argument** an implementer had to carry in their head.
under F16 the two absent-reads are **different values** — `false` for the version state, `null` for
an expiry — so the poll's target type (`{ status, expire }`) cannot even hold the off-token. ⇒
**a property that was true-but-argued became true-by-type**, which is `rule.prefer.prevent-over-correct`
rung 1 arriving somewhere it was not aimed.

### 🔴 and a versioning timeout is materially worse than a lifecycle one

on a lifecycle timeout the remedy is *"re-plan and re-apply"* — the put is a replace-all, so a retry
is free. on a **versioning** timeout it is not: the write may have already landed, and by **I-1**
`Enabled` is a **one-way door**. so the same throw carries a different instruction — *the write may
have landed; re-read before you retry* — and an error that says only "timed out, retry" invites a
consumer to re-issue a call whose first attempt they cannot undo.

## .the `[tn]` timeline

the narrative shows a phantom UPDATE and a shrug. the timeline names the predicate that has to
change and the timeout that must not be swallowed.

```
given  [case5] a fresh bucket
  and  a wish with transitions: [] and BOTH new sub-rules set

  when [t0] apply writes the lifecycle and immediately re-reads
  then  the poll compares the WHOLE owned rule to desired —
        objects.transitions AND objects.expire
        AND versions.expire
        AND multiparts.expire
   and  it does NOT declare stability on transitions.length alone
   and  🔴 the compare is CANONICAL, not a raw serialize — `transitions: []`
        and an omitted array are one state with two written forms, so a
        literal compare would never converge  (F11, owed at three nested
        sites under F16 rather than one flat one)

  when [t1] aws returns the pre-write state on the first read
  then  the stable-read counter RESETS to zero, it does not merely pause
        (a flap must not accumulate toward stability)

  when [t2] the poll reaches its deadline without stability
  then  it THROWS a HelpfulError — the class this repo already uses for a poll
        that never settled (getOneCloudwatchLogGroupReportDistOfPattern.ts:124,
        'CloudWatch Logs Insights query timed out')
   and  the error carries the desired config and the last-read config
   and  it does NOT return the stale read-back

  when [t3] apply returns
  then  the returned bucket equals what an independent fresh read would return
   and  an immediate re-plan by the CALLER reads KEEP, not only a later one

  when [t4] a bucket declares transitions AND both sub-rules
  then  the same predicate holds — the widened check must not regress
        the transition-only case the extant poll already covers

  when [t5] an EXTANT bucket changes ONLY a sub-rule
            (versions.expire.after: {days:30} -> {days:60}, all else unchanged)
  then  the poll must wait for the NEW value to read back
   and  it must NOT be satisfied by the PRE-PUT rule, whose transitions.length
        is identical to desired both BEFORE and AFTER the write

  when [t5c] an EXTANT bucket changes ONLY versions.expire.keep
            (null -> 5, and .after unchanged)                    ← F18
  then  the poll must wait for NewerNoncurrentVersions to read back
   and  🔴 it must NOT be satisfied by a check on NoncurrentDays alone —
        the container holds TWO fields and only one moved, so a poll keyed
        on the age field reads "already correct" and returns at once

  when [t5b] an EXTANT bucket changes ONLY versions.status
            (enabled -> suspended, versions.expire unchanged)
  then  🔴 the LIFECYCLE poll must not be entered at all — no lifecycle key
        changed, and F16's one object spans TWO aws calls
   and  the VERSION-STATE poll [t6] runs instead
   and  a poll keyed on "the lifecycle object changed" would fire here wrongly,
        wait on a config nobody wrote, and time out  (F16 sub-call 2)

  when [t6] apply writes versions: { status:'enabled', … } on a fresh bucket  # cell 1
  then  a poll waits until GetBucketVersioning returns Status == the desired status
   and  it compares the VALUE, never a proxy for it
   and  an ABSENT Status (the empty body) counts as not-yet, never as stable
   and  the same poll covers 'enabled' -> 'suspended'             # cell 3
   and  it is NEVER entered for versions: false, which issues no call at all
   and  🔴 it polls versions.STATUS only — versions.EXPIRE is a lifecycle key
        and belongs to [t0]'s poll, despite the two sitting in one object

  when [t7] the versioning poll reaches its deadline without stability
  then  it THROWS, same class and shape as [t2]
   and  it does NOT return the stale read-back
   and  the error says the write MAY ALREADY HAVE LANDED and to re-read first
   and  it does NOT advise a bare retry
        (I-1: 'Enabled' is a one-way door, so a blind re-issue is not free)
```

### what the timeline catches that the narrative does not

- **`[t1]`** — prose says "poll until stable". it hides the difference between *reset on
  mismatch* and *pause on mismatch*. the extant code resets (correctly); a rewrite could easily
  drop that and accept 3 non-consecutive matches across a flap, which proves less than one match.
- **`[t2]`'s "does NOT return the stale read-back"** — a timeout that gives up quietly is exactly
  the phantom-UPDATE bug dressed as a graceful degrade. a **throw**, not a shrug: it is our write
  that has not landed, so it is server-side and retryable. ⚠️ the class is `HelpfulError`, not the
  `MalfunctionError` the first pass named — `helpful-errors` exports no such class (defect 26); the
  repo's own timed-out-poll precedent throws a plain `HelpfulError`.
- **`[t3]`'s "by the CALLER"** — the narrative sees vlad's terminal. it cannot see that a correct
  object out of `setS3Bucket` is a *weaker* claim than a correct next independent read. the second
  is what the plan actually uses.
- **`[t4]`** — a regression guard the narrative has no reason to mention.
- **🔴 `[t5]` — the worst path, and the one this case originally missed.** every step above it runs
  on a **fresh** bucket, where `live` reads `null` first and `undefined === 0` accidentally forces
  the poll to wait. on an **update** that accident is gone: `transitions.length` is unchanged on
  both sides, so the *first* read — the stale pre-put rule — satisfies the predicate outright. three
  stale reads pass in ~3s and stability is declared with **not one byte of the change observed**.
  the extant poll offers this class of write **no protection at all**, and it is exactly `#35`'s
  steady state ("change a retention number, re-apply"). added by the r1 self-review.
- **`[t6]`'s "never a proxy for it"** — the narrative cannot show a *shape* defect, only a symptom.
  the versioning poll's correctness rests entirely on a choice the prose would never surface: compare
  the value, not a stand-in for it. `[t5]` proves what the proxy habit costs; `[t6]` is where the
  habit must not be copied.
- **`[t6]`'s "NEVER entered for versions: false"** — the one beat that is a **claim about
  unreachability** rather than about behaviour. it is what makes the versioning poll safe despite an
  absent-read that is exactly as ambiguous as the lifecycle one, and it is invisible unless stated.
  🟢 **F16 demoted it from a claim to a type fact** — the poll's target is `{ status, expire }`,
  which cannot hold `false` — but it stays in the timeline because a *type* fact still needs a test
  when the value crosses a wire.
- **🔴 `[t5b]`** — added by the F16 propagation, and it is the beat prose cannot reach at all. it
  asserts a poll that must **not** fire. one declared object now spans two aws calls, so "did the
  object change?" is the wrong trigger for either poll — and every narrative of a successful suspend
  reads identically whether the implementer keyed on the object or on the key. ⇒ **the cost of the
  one-verb-for-two-verbs trade F16 took, stated as a testable beat rather than as a caveat.**
- **🔴 `[t7]`'s "does NOT advise a bare retry"** — added by peer review r1. every other timeout in
  this vision is safely retryable; this one is not, because the write it may have completed is
  irreversible (**I-1**). an error copied from `[t2]`'s wording would be correct in class and
  **wrong in instruction** — it would tell a consumer to re-run the one call they cannot undo.

## .the consequence the first pass missed — a refused apply, for the whole wish

a stale read does not merely mislead a human. `apply --plan <file>` **replans first**
(`applyChanges.js:21`), then calls `assertPlanStillValid`, which throws
`BadRequestError('plan is stale')` when `originalPlan.hash !== currentPlan.hash`
(`validate.js:10-19`). that hash is **sha-256 over the entire serialized changes array**
(`hashChanges.js:10-16`).

three consequences follow, none of them in the narrative:

1. **a flappy read between the two plans aborts the apply outright.** the operator ran `plan`, read
   it, approved it — and `apply` refuses with *"The infrastructure state has changed since this plan
   was created."*
2. **the blast radius is the whole wish, not the bucket.** the hash spans every resource, so one
   eventually-consistent lifecycle read invalidates the plan for every other resource in the file.
3. **it is misattributed by construction.** `BadRequestError` is caller-must-fix — a transient aws
   consistency window is reported to the operator as *their* staleness, and the advice is "make a
   new plan", which will usually appear to work. **a defect that clears itself on retry is a defect
   nobody ever files.**

this is why F6's widened predicate is not a nicety: the poll is the only guard between an
eventually-consistent read and a plan-hash mismatch.

## .why this is a critipath

- **frequency** — every fresh bucket, every ci run that applies then asserts. high.
- **cost** — a phantom UPDATE that cannot be reproduced by hand. this is the most expensive class
  of defect in the repo's own record: `hazard.local-green-cicd-red` documents the same signature
  (green locally, red in ci, unreproducible), which costs hours before anyone suspects state
  rather than code. it also gets **misfiled as flake**, so it survives triage.

`freq × cost` is high on both terms → critipath.
