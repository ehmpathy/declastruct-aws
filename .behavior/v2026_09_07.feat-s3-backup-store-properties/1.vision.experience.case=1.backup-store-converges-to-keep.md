# case=1 — backup store converges to KEEP

**feel** happy · **care** critipath · **actor** `consumer` · **cells** 1, 2, 7, 8, 13, 14, 19, 20

🔴 **the WIDEST case, not the densest.** all four properties, declared at once on a fresh bucket,
driven plan → apply → plan — **eight cells, one walk.** it ranks **fifth** by boundary-density, at
**4** boundaries: its eight cells are **four properties × two states**, which is the same CREATE/KEEP
pair four times over, and four parallel instances of two boundaries is not eight boundaries.

⇒ **width and density are different virtues, and c1 has the first.** it is the breadth walk the
guardrail asks for — the one case that puts all four properties through one lifecycle — which is why
it stays a critipath at fifth place. the census ranks **c10** first (8 boundaries, the only actor

## .narrative

vlad is on the `ahbode/infrastructure` side. he wants one thing: **a git-backup bucket in the camp
account that will not quietly bill him.** he opens the wish file and writes the bucket he wants.

```ts
const gitBackupStore = DeclaredAwsS3Bucket.as({
  name: 'ahbode-camp-git-backup',

  // a backup store is never public. 'blocked' expands to all four blocked — F15
  access: { public: 'blocked' },

  lifecycle: {
    // the current copy of every file is kept forever — that is the point of a backup
    objects: { expire: null, transitions: [] },

    // keep every write recoverable — a grove that pushes a corrupt tree must be undoable
    versions: {
      status: 'enabled',

      // versions are on, so old ones would otherwise accrue forever
      expire: { after: { days: 30 }, keep: null },   // by age; no count floor (F18)
    },

    // the grove is an ec2 box that stops itself when idle; a stopped writer strands parts
    multiparts: { expire: { days: 7 } },
  },

  tags: { managedBy: 'declastruct', purpose: 'git-backup' },
});

return [gitBackupStore];
```

🟢 **one object, four keys.** `access` is a **nested field** (F10) and `versions` now lives inside
`lifecycle` (F16), so the write ORDER that `[t1]` asserts is ours to hold inside `setS3Bucket` —
never an order the consumer's `getResources()` array must carry.

🔴 **the first he notices is that the type would not let him write `status` alone.** `expire` is a
required key on the same object — he has to put a duration or `null` beside it. he pauses for a
second, thinks *"right, versions are on, old ones pile up"*, and writes `{ days: 30 }`. that pause is
the whole point: the cost leak the wish warns about is a decision he was **forced** to make.

⇒ **F16 moved this from "forced to type" to "cannot be typed otherwise."** under the flat shape,
`expireNoncurrentVersionsAfterDays` was a required field he could satisfy with `null` while he never
read the `versions` line at all. under the nest, the key he must satisfy sits **on the object he just
turned on** — the two are one keystroke apart, and that adjacency is the guard (`c11`).

he runs plan.

⚠️ **and one declared key spans two of those calls.** `lifecycle.versions.status` goes out on the

**`🎉 everything is in sync!` is the aha, and it is declastruct's own line** — it prints only when
every change reads KEEP (`planChanges.js:76-80`). the plan renderings above are the verified stdout,
not a sketch: `🔮 plan changes...` (`:21`), `○ <slug>` (`:37`), `├─ ✔ done in Xs` (`:45`),

annotated `Remote` / `Desired` (`:63-67`, `getDisplayableDiff.js:28-36`).

he has been burned by permadrift before — a plan that reads UPDATE forever
because the tool's shape and the cloud's shape disagree about a value they both agree on. this one
just says KEEP. he can put the wish in ci and trust a non-empty plan to mean a real change.

## .the `[tn]` timeline

the narrative shows the felt moment (the forced `null`, the second plan). the timeline tests the
claim underneath it: that every one of the four canonicalizations round-trips.

### ⚠️ what "round-trips" means here, precisely

declastruct decides KEEP by
`serialize(omitReadonly(remote)) === serialize(omitReadonly(desired))`
(`declastruct@1.7.3/dist/domain.operations/plan/computeChange.js:13-18`), and **the desired side is
the caller's object verbatim — it is never round-tripped through the cast**
(`DeclaredAwsEc2LaunchTemplate.ts:100-102`). so the cast governs one operand only, and the claim
above is really two:

1. the **remote** operand: each read collapses aws's shape to our shape (the cast's job).
2. the **desired** operand: each property admits **exactly one written form per state**, so the
   caller's object is already canonical and needs no collapse.

(2) holds for **three** of the four — `versions` is a closed union and the two lifecycle fields are
`number | null`, so each state has exactly one written form.

🔴 **`access.public` does NOT satisfy (2)** — the blocked state has **three** written forms:

| the caller writes | means |
|---|---|
| `access: { public: 'blocked' }` | all four true — the explicit token (F15) |
| `access: { public: s3BucketAccessPublicBlocked }` | all four true, spread from the preset const |
| `access: { public: { acls: { block: true, … }, policies: { … } } }` | all four true, written out |

🟢 **F15 removed a FOURTH form at the type.** `access` is required and non-nullable, `public` is
required and typed `'blocked' | DeclaredAwsS3BucketAccessPublic` ⇒ **no `null` occurs in this
subtree at all**, so neither `access: null` nor `access: { public: null }` is writable.

⚠️ **and that does NOT retire the canonicalizer** — the overclaim invites itself and is false. the
preset-const arm and the bare-literal arm still serialize differently without F2's `static nested`
clause, and the **token arm never enters hydration at all**. three forms still need collapse to one.

⇒ **so it needs a canonicalizer in the bucket's constructor**, exactly as its peer does:
`DeclaredAwsEc2LaunchTemplate.ts:126` runs `asCanonicalEc2InstanceMetadataOptions(props.metadataOptions
?? null)` for the identical reason — *"metadataOptions has three ways to say secure."*

🔴 **without it, `null` and the spread serialize differently and the plan reads UPDATE forever** —
the permadrift this wish exists to close, on the field the wish's own `.why` is about.

⚠️ F2's `static nested` registration handles forms 2 and 3 (hydration tags both with `_dobj` at
compare time), and **it cannot reach form 1** — a bare string literal never enters hydration. the
canonicalizer is a second, separate obligation, owed at `2.1.criteria` as a blueprint line.

🔴 **and F14 doubled BOTH obligations, because the shape now nests twice.**

| obligation | at one level (pre-F14) | at two levels (`access: { public }`) |
|---|---|---|
| `static nested` | on the bucket, for the block dobj | on the bucket for `access`, **and** on the access dobj for `public` |
| the canonicalizer | one call, on `props.publicAccessBlock` | it must reach `props.access.public` and expand the `'blocked'` token to the four booleans |

🟡 **F14's own entry flagged a THIRD cost here — the outer `access: null` form — and F15 closed it
at the type.** that is strictly better than a canonicalizer clause, since **a type cannot be
forgotten**. ⇒ what remains is the row above: two registrations, and one expansion of the token.

🔴 **the canonicalizer must run at CONSTRUCTION, on both operands**, or `'blocked'` and the spread
serialize differently and the plan reads UPDATE forever — the permadrift this case exists to close,
on the exact field the wish's `.why` is about. carried to `2.1.criteria`.

3. 🔴 **none of the four may be declared `readonly`.** the comparison runs `omitReadonly` on both
   operands first, so a readonly field is excluded from the diff outright — a permanent false KEEP,
   the mirror of permadrift and strictly worse (permadrift is loud; this is silent).
   `DeclaredAwsS3Bucket.readonly` is `[]` today and must stay that way for these four.

   ⚠️ **the rule is one sentence but the mechanism differs by grain** — verified in
   `domain-objects/dist/manipulation/getReadonlyKeys.js`, not inferred from the name:

   | dobj | grain, verified | what `omitReadonly` strips |
   |------|-----------------|---------------------------|
   | `DeclaredAwsS3Bucket` | **DomainEntity** — `DeclaredAwsS3Bucket.ts:44` | metadata keys **∪ `static readonly`** — so a readonly entry here really would erase the field from the diff |
   | `DeclaredAwsS3BucketLifecycle` | **DomainLiteral** — `DeclaredAwsS3BucketLifecycle.ts:32` | **metadata keys only** — `static readonly` is *silently ignored* on a literal, *"due to their nature"* |

   ✅ **today both strip nothing at all**: the bucket declares `metadata = []` (`:60`) and
   `readonly = []` (`:65`), and the lifecycle declares neither. so all four new properties reach the
   comparison intact as the code stands — **the obligation is to keep it that way**, not to change it.

   so the hazard is real on the bucket and **inert-but-misleading** on the lifecycle: a `readonly`
   entry there would not cause a false KEEP — it would have no effect at all, while it reads as
   though it did. both are reasons to declare none of the four readonly; only the first is a
   correctness bug.

4. ✅ **the two operands are re-instantiated before the compare, which is what makes F2 work.**
   `omitReadonlyDeep` ends with `new Constructor(objWithoutReadonlyValues)`, so **both** sides pass
   through the dobj constructor — and therefore through `static nested` hydration — immediately
   before `serialize`. that is why a caller who spreads the preset const `s3BucketAccessPublicBlocked`
   and a caller who writes the four booleans as a bare literal compare **equal**: hydration tags
   both with `_dobj` at compare time, not merely at construction time.

### 🔴 the `[t4]` note — the other written forms are STEPPED, not merely argued

cell 8 is a **critipath**, and axis C's `value` now arrives in **three written forms** (the table
above). all three must land on cell 8, and the narrative exercises **only the token**. the other two
rest on an argument rather than a step:

| form | what its equality rests on | proven by |
|---|---|---|
| `'blocked'` | 🔴 the **constructor's canonicalizer** — a string never enters `static nested` | the narrative |
| the spread | hydration at compare time (`omitReadonlyDeep` re-instantiates both operands) | `[t4]` |

🔴 **a code-level proof is not a demonstrated experience.** a form that failed to compare equal would

⚠️ **note what makes the beat worth its line: it needs a SECOND consumer.** one wish cannot declare

### 🔴 the `[t5]` note — the literal on the FIRST-SET path, where the defect is not a non-KEEP

⚠️ **added by peer review r2 (nitpick.2), and it is a sharper find than `[t4]`.** `[t4]` steps the
literal against a bucket that is **already written**, so it exercises **cell 8** (`value × set-same`)
alone. the census names **two** cells for `publicAccess`'s `value`, and the other one is **cell 7**
(`value × absent`) — the first `PutPublicAccessBlock`, issued **from the literal**, against a bucket
that has no block at all.

🔴 **the two cells fail in opposite directions, which is why one cannot stand in for the other:**

| cell | the literal's role | what a hydration mismatch produces | caught by |
|------|--------------------|-------------------------------------|-----------|
| **8** — `value × set-same` | the **desired** side of a compare whose remote already matches | a spurious **UPDATE** — the permadrift | ✅ the suite's `all resources show KEEP after apply` |
| 🔴 **7** — `value × absent` | the **desired** side of a compare whose remote is `null`, **and the source of the write** | a **CREATE-diff** that names the wrong booleans, or a write issued from a mis-hydrated operand | ⛔ **no extant assertion** — a CREATE is the *expected* decision here, so no KEEP gate fires |

⇒ that asymmetry is the whole point: **cell 8's defect announces itself as a non-KEEP, and cell 7's
does not.** a CREATE on a fresh bucket is correct by construction, so a diff that renders the wrong
four booleans — or a `PutPublicAccessBlock` built from an operand that was never hydrated —
passes every convergence gate this wish adds. the second plan reads KEEP because the *remote* now
matches whatever was written, right or wrong.

⚠️ **and it needs a THIRD consumer, for the same structural reason `[t4]` needed a second.** `[t4]`'s
bucket is written by `[t1]`; a first-set demo cannot reuse it. so the beat is a fresh bucket and a
fresh caller — which is why the literal's first-set path had no place to land in a single-actor
narrative. the same blind spot as `[t4]`, one cell over, and one grade worse.

### ⚠️ the write-order note — `[t1]`'s third clause

`setS3Bucket` is **not atomic**. today it issues `createBucket` → (lifecycle put + poll ∣ lifecycle
del) → tag reconcile (`setS3Bucket.ts:48-96`); this wish adds **two more write surfaces**. so an
abort mid-sequence leaves a half-applied bucket, and **which half survives depends on the order the
writes were issued in.**

one order is worse than the others, and it is the obvious one:

| order | if a later write throws | verdict |
|-------|-------------------------|---------|
| the **version-state put first**, lifecycle later | the bucket is left **versioned with no noncurrent-expiry rule** — every write accrues a version no rule reaps | 🔴 **the exact cost leak this wish exists to close, live as a transient** |
| lifecycle **first**, the version-state put later | the bucket is left with a reaper rule and no versions to reap | ✅ inert |

🔴 **F16 makes this order harder to get right, not easier.** `status` and `expire` are now two keys of
**one declared object** — so the sequence that separates them is invisible from the declaration, and
a reader of `setS3Bucket` sees two writes fed by one field with no type-level reason they must be
ordered. ⇒ the `.note` is not documentation; it is the only surviving trace of the constraint.

### 🔴 and the sharper reason, which the cost leak hides

the row above frames this as a **transient**, and a transient converges. but the versioning put is
not a transient write — **it is a one-way door (invariant I-1).**

so a partial apply that lands the version-state put and then throws leaves the consumer with a
bucket **versioned by accident**, which they never declared as a completed act. their natural next
move is to undo it — `versions: false` — and **case=3's guard rejects them.** c3 demos that
rejection for a consumer who turned versions on deliberately; this consumer acquired them as the
residue of a failure, and meets the same wall.

⇒ **that is what makes the order an obligation rather than a preference.** every other write in the
sequence is reversible on a retry; this one is not. issue it **LAST**, so the irreversible step is
the one that only runs when every reversible step has already succeeded.

both orders converge on the next apply, so neither is a defect — which is why this is a `[tn]`
clause rather than its own case. **it is an order the implementer can get wrong for free.**

⇒ this is the `retried`-from-half-applied value of the **`concurrency / time`** axis
(`1.vision.experience.dimensions.md` axis E). it is graded there as sharp · **alter** — because its
fail-safe is c3's guard verbatim, so it crosses no boundary c3 does not already cross.

### what the timeline catches that the narrative does not

- **`[t1]`'s "not the pre-write state"** — the narrative cannot see that `setS3Bucket` returns a
  read-back object. if that read lands inside aws's write window it returns stale values, and the
  caller's own re-plan reads UPDATE while vlad's terminal reads KEEP. that split is invisible in
  prose. → its own case, **c5**.
- **`[t3]`** — the narrative stops at one clean re-plan. a second *apply* is the harder claim
  (`rule.require.guaranteed-idempotency`): the lifecycle put is a replace-all, so a re-apply
  rewrites the same rule and must not perturb the read-back.
- **`[t0]`'s "no property silently absent"** — a property that never reaches the diff looks
  identical to a property that matches. the narrative would read as success either way.
