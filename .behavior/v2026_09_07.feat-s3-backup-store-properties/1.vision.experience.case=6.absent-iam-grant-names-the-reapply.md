# case=6 — an absent iam grant names the re-apply

**feel** sharp · **care** critipath · **actor** `system:ci` · **cell** the ci-only gate

**the actor axis earns its keep here.** this cell exists only in the `system:ci` row: the consumer
at a terminal has admin creds and never meets it. ci runs as `ehmpathy-demo-oidc`, and this wish
adds four api calls that role cannot make.

## .narrative

the pr is green locally. `rhx git.repo.test --what integration` passes on marina's laptop, every
acceptance case included. she pushes. ci **plans clean**, then goes red at apply:

```
🪄  apply changes...

○ [CREATE] ehmpathy-mail-inbound-demo

{
  "cause": "AccessDenied: User: arn:aws:sts::...:assumed-role/ehmpathy-demo-oidc/GitHubActions is not authorized to perform: s3:PutBucketVersioning on resource: arn:aws:s3:::ehmpathy-mail-inbound-demo",
  "bucket": "ehmpathy-mail-inbound-demo",
```

## .the grants this wish adds

verified absent from the **inline** statements of `demoPermissionsPolicy`
(`provision/aws.auth/resources.common.ts:328-343`), which today grant
`s3:Get/PutLifecycleConfiguration`, `s3:Get/Put/DeleteBucketPolicy`, `s3:Get/PutBucketTagging`, and
the bucket crud — and none of these four:

```
s3:GetBucketVersioning            ← probably covered by managed ReadOnlyAccess
s3:PutBucketVersioning            ← NOT covered. the real gap
s3:GetBucketPublicAccessBlock     ← probably covered by managed ReadOnlyAccess
s3:PutBucketPublicAccessBlock     ← NOT covered. the real gap
```

⚠️ **the read/write split is what makes this case's diagnosis harder than it first looks.** the
bundle also attaches the managed `ReadOnlyAccess` policy (`resources.common.ts:39`), whose
`s3:Get*` scope covers the two reads. ✅ **verified against the live policy document, not inferred** —
the managed `ReadOnlyAccess` grants `"s3:DescribeJob"`, **`"s3:Get*"`**, **`"s3:List*"`** on
`"Resource": "*"` (fetched; this closed **Q-6**). ⇒ so this case's central claim — **the plan reads
clean and only the apply throws** — is now fact rather than inference, and that upgrade matters: it
is precisely the half that makes the diagnosis hard, so it was the worst claim in the vision to leave
on a well-known-scope guess.

add all four to the inline statements regardless: the two reads become explicit rather than
inherited, and an explicit grant is cheaper than a dependency on a policy aws controls **and can
narrow without notice**.

the two lifecycle sub-rules need **no new grant** — they ride the extant
`s3:Get/PutLifecycleConfiguration` on the same commands. only the two bucket-level properties open
new api surface.

## .the fail-safe — why this must throw, not degrade

`rule.forbid.plan-fail-on-apply-guided-prereq` says a plan-time `get` must degrade rather than
hard-throw on a precondition an apply is designed to guide. **this case is the exception, and the
line is worth a statement.**

that rule's own test asks: *is this the KNOWN "prereq off" signal, and does a `set` guide the fix?*

- the **absent-signal** error — **yes.** a known absent-signal, and the apply writes it.
  → degrade to `null` (case=2, `[t1]`). ⚠️ its exact name is UNVERIFIED; case=2 carries the
  obligation to read it off the live api before the detector is written. **that obligation carries
  double weight here**, because a detector matched on the wrong name does not merely fail to
  degrade — it lets an absent block fall through to the `AccessDenied` path below, so a routine 404
  gets reported to the operator as an iam failure and sends them to re-apply a policy that was
  never the problem.
- `AccessDenied` — **no.** it is not an absent-signal at all, and no `set` of ours can grant an iam
  permission. to degrade it to `null` would report "this bucket has no public-access block" when
  the truth is "we were not allowed to look" — a phantom CREATE, then an apply that fails deeper
  and dirtier. that is textbook `rule.forbid.failhide`.

so the two live at the **same catch**, one line apart, with opposite obligations. that adjacency is
the real hazard of this case.

### the fail-safe grade — **all five clauses**, at the edge

🔴 **this table graded three clauses for nine rounds, and peer review r2 (verified15, nitpick.3) was
right about the cost: it made this case's proof non-comparable with its sharp siblings.** the census
rubric defines **five**; c2, c4, c5, c9 and c10 grade five; c6 graded the three it happened to have
prose for. ⚠️ **and the ungraded clause was not vacuous here — it is the one this case's own `[t1]`
asserts an obligation about.**

| # | clause | grade |
|---|--------|-------|
| 1 | **fast** | ✅ thrown at the first denied write, before any later resource in the wish is touched — never swallowed into a partially-applied bucket |
| 2 | **loud** | ✅ the error names the **principal** — `assumed-role/ehmpathy-demo-oidc/...` — which is the single token that identifies this failure class |
| 3 | **teaches the fix** | ✅ names BOTH provisions, in the right order, and links the walkthrough. a one-target re-apply is the trap the hazard brief exists to warn about |
| 4 | **holds the limit** | **vacuous at this cell** — a denial is not a boundary value; there is no last-valid-input to hold. the limit is the grant, and it is held by iam, not by us |
| 5 | 🔴 **drops no data silently** | ✅ **and this is the clause `[t1]` was already about.** the apply leaves the bucket **partially written** — a state neither the wish nor the prior state describes — so the obligation is that the failure **name which writes landed and which did not**. it is met on two counts: (i) the error is thrown at the denied call, so the landed set is exactly the writes that preceded it in the fixed order c1 `[t1]` pins (`PutBucketVersioning` **last**); (ii) declastruct **replans before every apply**, so the next run reads the true remote state and computes the remainder — the partial state is recovered by convergence, never carried silently forward |

⇒ 🔴 **the partial apply is a real hazard and it is NOT a silent one** — which is precisely why the
clause needed a grade rather than a timeline assertion. ⚠️ **and clause 5's first count is the
argument that makes the hazard legible at all: it rests on a FIXED write order.** were the four
writes issued in an arbitrary order, "which landed" would be unknowable from the error alone, and an
operator could not tell whether the irreversible `PutBucketVersioning` had run. ⇒ *this case is a
second consumer of `setS3Bucket.ts`'s write-order obligation, and the `.note` that obligation owes
should name **both** c1 and c6 as its reasons.*

## .the `[tn]` timeline

the narrative shows a good error. the timeline pins where the denial actually lands, the
discrimination the narrative glosses over, and the two-target claim.

```
given  [case6] a ci run as ehmpathy-demo-oidc whose INLINE policy lacks the four grants
  and  the bundle attaches managed ReadOnlyAccess (so s3:Get* is covered)

  when [t0] plan reads GetBucketVersioning and GetPublicAccessBlock
  then  both SUCCEED — the reads ride ReadOnlyAccess
   and  the plan reports a correct CREATE
   and  a clean plan is therefore NOT evidence the grants are live

  when [t1] apply issues PutBucketVersioning
  then  aws throws AccessDeniedException
   and  the apply fails HERE, not at plan
   and  the bucket is left partially applied — the failure must name which
        writes landed and which did not

  when [t2] a read is denied instead (a narrower role than assumed above)
  then  the read PROPAGATES the error — it does NOT return null
   and  the same catch that degrades the absent-signal error to null
        MUST NOT catch AccessDenied
        (the two obligations sit one line apart at one boundary)
   and  the absent-signal is matched on the name aws ACTUALLY emits — read live,
        never assumed (see case=2; an assumed name misroutes BOTH branches)

  when [t3] the error surfaces in the ci log
  then  it names the assumed-role principal
   and  it names BOTH provision paths, not only the oidc one
   and  it links howto.reapply-demo-oidc-role

  when [t4] ONLY the oidc provision is re-applied
  then  ci passes
   and  a later LOCAL run that must CREATE the property fails the same way
        (the mirror-image drift — the hazard's whole point)

  when [t5] both provisions are re-applied and each plan shows an UPDATE
  then  ci and local both pass
   and  a create-from-scratch of the bucket succeeds under each role
```

### what the timeline catches that the narrative does not

- **`[t0]`'s last `and`** — the sharpest correction in this case. **a clean plan is no evidence at
  all about the write grants**, because the reads ride a different policy. anyone who reasons
  "plan was green, so permissions are fine" is wrong, and the narrative alone would let them.
- **`[t1]`'s "partially applied"** — three writes land in sequence (versioning, block, lifecycle).
  a denial on the first leaves a bucket in a state neither the wish nor the prior state describes.
  prose reads it as one atomic "apply failed".
- **`[t2]`** — the narrative shows a denial handled well. it cannot show that the *correct*
  handler for this case and the *correct* handler for case=2 are neighbours in one `catch`, and
  that a single `||` widens one branch and silently converts a loud iam failure into a phantom
  CREATE.
- **`[t4]`** — the narrative stops at "green". the timeline states the trap the hazard brief was
  written for: a one-target re-apply looks like success and simply moves the failure to the other
  environment, where it surfaces later and is diagnosed from scratch.
- **`[t5]`'s "each plan shows an UPDATE"** — a re-apply that reports "up to date" proves the
  policy was already current, not that the grant is live. the hazard brief calls this the
  **red herring**; only a visible UPDATE proves the target moved.

## .why this is a critipath

- **frequency** — **certain, exactly once.** the first ci run after this wish merges. that is
  frequency 1, not 0 — the boundary case in `define.experience._.axis=care` does not apply.
- **cost** — high and, more importantly, **misattributed by default**. the repo's own hazard brief
  documents that the diagnosis costs hours, because the symptom (green local, red ci) reads as a
  code defect. the fallback — a human reads a raw `AccessDenied` stack and works it out — is
  exactly the cost this case exists to remove.

`freq × cost` intolerable → critipath. and the mitigation is cheap: name the principal, name both
targets, link the walkthrough.
