# case=7 — a versioned fixture cannot be torn down

**feel** sharp · **care** critipath · **actor** `system:ci` · **cells** 1, 2 × `A=system:ci`

🔴 **this is the one cell in the space whose failure is unrecoverable by the actor that causes it.**
the acceptance fixture is not "a bucket like any other" for the ci actor.

**the failure lands after the apply reports success**, on a teardown path no plan ever renders.

## .narrative

**marina** adds the wish's headline property to the acceptance fixture — the smallest possible edit,
one changed line — so the new field is exercised end-to-end:

```ts
const mailStore = DeclaredAwsS3Bucket.as({
  name: 'ehmpathy-mail-inbound-demo',
  access: { public: 'blocked' },
  lifecycle: {
    objects:    { expire: null, transitions: [ … ] },
    versions:   { status: 'enabled', expire: null },   // ← the edit
    multiparts: { expire: null },
  },
  tags: { managedBy: 'declastruct', purpose: 'acceptance-test' },
});
```

⚠️ **the edit is one key on an object a reviewer already has in view** (F10: nested fields). that is
the best case for legibility, and it is still not enough — no part of that line says *one-way door*.
⇒ the trap is not that the edit is hidden; it is that **the cost is invisible at the site of the
decision**.

🔴 **F16 made the edit LARGER and the trap no smaller, and that is this case's sharpest read of the
verdict.** marina no longer flips a token; she replaces `versions: false` with a two-key object, and
the forced key makes her answer a second question (`expire`) while she does it. **two deliberate acts
where there was one** — and she still gets no signal about the door, because the door is a property
of neither key. ⇒ **F16's forced key buys attention on the COST DIMENSION it names (the expiry) and
buys none on the one it does not (irreversibility).** that is the honest bound on *"a forced key
makes the consumer think"*, and c7 is where it is measured.

marina's run is green. `plan` reads CREATE, `apply` succeeds, the re-plan reads KEEP. **every
assertion in the suite passes**, the property round-trips exactly as case=1 promises, and she merges
with the quiet satisfaction of a one-line PR that did precisely what it said.

🔴 **that green is the whole trap, and it is why this case has TWO actors.** marina gets no signal —
at any moment she can observe — that she has just made the fixture permanently undeletable. she
writes the line; **the operator on the next teardown** meets the consequence. what separates the act
from its cost is not time, as in c10, but a **person**: the one who could have chosen differently
never sees the failure, and the one who sees it cannot undo it.

then ses delivers a piece of mail into the bucket, as it has on every run for months. and the next
teardown fails:

```
BucketNotEmpty: The bucket you tried to delete is not empty
```

the operator empties it — `aws s3 rm s3://ehmpathy-mail-inbound-demo --recursive` — watches it
report every object removed, and runs teardown again.

```
BucketNotEmpty: The bucket you tried to delete is not empty
```

**the bucket is empty and aws will not delete it.** every object delete wrote a **delete marker**,
each marker is itself a version, and `DeleteBucket` counts versions and markers as contents.

so they reach for the obvious escape and set `versions: { status: 'suspended', … }`. it does not help
either — under suspension a delete *still* writes a marker. then they try to remove the versions directly,
and the demo role refuses: it holds `s3:DeleteObject` and **not** `s3:DeleteObjectVersion`.

⇒ the fixture is now an orphan that the suite cannot clear, the operator cannot clear, and — because
**s3 bucket names are a global namespace** — nobody can ever reuse the name. clearance needs admin
credentials, i.e. the same interactive human-only path case=6 already documents.

### 🔴 why this is the trap and not merely a hazard

**the obvious place to add the demo is the one place it must not go.** `mailStore` is the natural
fixture — it already exists in the acceptance wish, it is already a bucket, and one line enables the
property. it is also **the only bucket in the suite that receives objects.** a correct instinct
(*"exercise the new field on the fixture we already have"*) walks straight into the one combination
that cannot be undone.

### the facts, fetched from aws — not inferred

| fact | source |
|------|--------|
| *"All objects (including all object versions and delete markers) in the bucket must be deleted before the bucket itself can be deleted."* | `API_DeleteBucket.html` |
| *"If bucket versioning is enabled, the operation **inserts a delete marker**, which becomes the current version of the object. To permanently delete an object in a versioned bucket, you must include the object's `versionId`."* | `API_DeleteObject.html` |
| under **suspended** versioning: *"if there isn't an object with a null `versionId`, and all versions of the object have a `versionId`, Amazon S3 **does not remove the object** and only inserts a delete marker"* | `API_DeleteObject.html` |
| the demo role grants `s3:DeleteObject`, and **not** `s3:DeleteObjectVersion` | `provision/aws.auth/resources.common.ts:45`, read in full |
| aws names `DeleteObjectVersion` as the separate action required *"to delete a specific version of an object from a versioning-enabled bucket"* | `API_DeleteObject.html` |
| managed `ReadOnlyAccess` cannot supply the absent action | by construction — a read-only policy holds no delete |

⚠️ **the third row is the one that surprises.** the natural escape — suspend, then delete — is the
one legal retract aws offers (invariant I-1, case=3), and it does **not** undo this. the door is
one-way for object semantics too, not merely for the declared state.

## .the fail-safe — two rungs, per `rule.prefer.prevent-over-correct`

### rung 1 — prevent: the fixture obligation

🔴 **a bucket that declares a NON-NULL `versions` — `'Enabled'` OR `'Suspended'` — must never
receive an object, in any test at any grain.** the property is demonstrated on its **own object-free
fixture**, never folded onto a bucket that already carries writes.

> ⚠️ **the obligation was scoped to `'Enabled'` alone for two rounds; peer review r1 caught it, and
> this case's own verified facts are what convict the narrower text.** aws's `DeleteObject` page —
> quoted below and in the census — says that under **suspended** versioning a delete *"inserts a
> delete marker … If there isn't an object with a null `versionId`, and all versions of the object
> have a `versionId`, Amazon S3 **does not remove the object**"*. ⇒ a `'Suspended'` fixture that ever
> receives an object faces the **identical** `BucketNotEmpty` orphan, for the identical reason, with
> the identical loss of a globally-unique name.
>
> 🔴 **and the narrow scope was worse than merely incomplete — it pointed at the escape hatch.** this
> case's own §*"`Suspended` does NOT restore the safe teardown"* exists precisely to refute *"just
> suspend it before del"*. an obligation that named only `'Enabled'` implied, by omission, that
> `'Suspended'` was the safe value — **the exact misread the section above it was written to
> prevent.** ⇒ the rung-1 guard now keys on **non-null**, which is the property that actually predicts
> the hazard.

this holds for all four surfaces the wish owes (the five communicator integration tests, the
transformer unit cases, the `s3Bucket.journey` orchestrator test, and the acceptance fixture) — and
the journey test states the premise it depends on outright: *"aws requires an empty bucket to delete;
**this journey never puts objects, so del is clean**"*. that sentence is what a `status: 'enabled'`
invalidates.

| fixture | receives objects? | `lifecycle.versions` | verdict |
|---------|-------------------|-----------|---------|
| the journey bucket | never | must stay `false`; a versioned case takes its **own** object-free bucket | safe |
| `mailStore` (acceptance) | **yes** — ses writes inbound mail | must stay `false` | safe **only while `false`** |
| a new backup-store fixture | none | `{ status: 'enabled', expire }` | safe **only while object-free** |

🟢 **F16 gave the rung-1 guard a cleaner key than `non-null` was.** the guard predicts the hazard from
*"is version history on?"*, and under F16 that is exactly `versions !== false` — a **type-level**
discriminant with no third state to misread. ⚠️ under the flat shape the same guard keyed on
`non-null`, which had to be **argued** into correctness after a first pass mistakenly read
`'Suspended'` as safe. ⇒ the guard's logic is unchanged and the room for that particular misread is
gone: a reader who asks *"is `suspended` safe?"* is now asking about a value **inside** the on-branch,
which is visibly not the off-token.

### rung 2 — teach: `BucketNotEmpty` must name the real cause

`delBucket.ts` already fails **loud** and **fast** — it rethrows on a non-empty bucket, and its
`.note` records that as deliberate: *"a non-empty bucket fails loud (by design — we never silently
purge objects)"*. ✅ that guarantee is correct and stays.

🔴 **what it does not do is teach the fix.** aws's `BucketNotEmpty` is silent on delete markers, on
`DeleteObjectVersion`, and on the admin path — so an operator who has *just emptied the bucket* reads
a message that appears to contradict what they observed. the repair is to wrap that one error with
what the operator cannot infer:

```
BucketNotEmpty: ehmpathy-mail-inbound-demo still holds contents

  why: aws counts object VERSIONS and DELETE MARKERS as contents. if this bucket has
       versioning enabled, `aws s3 rm --recursive` does not empty it — each delete
       writes a marker, and each marker is itself a version.
       a status of 'suspended' does NOT undo this.

  fix: remove every version and marker, which needs `s3:DeleteObjectVersion` —
       an action the demo role does NOT hold. use admin credentials:
         aws s3api list-object-versions --bucket ehmpathy-mail-inbound-demo
         aws s3api delete-object --bucket <b> --key <k> --version-id <v>

  note: a bucket name is GLOBAL. until this is cleared the name is unusable account-wide.
```

🟢 **its content was RULED IN on 2026-09-09 (F8 confirmed)**, exactly as case=3, case=4 and case=6
were: *name versions and markers, name `DeleteObjectVersion`, name the global namespace.* the shape
above renders through `helpful-errors` as message + serialized metadata, which is how this repo
throws. ⚠️ **the carrier half of F8 was never put to the council** — an evidence-settled question
rather than a live one, and c4's fail-safe table carries the observation that closes it.

### the fail-safe grade — **all five clauses**, at the edge

🔴 **added at verified21.** peer review r2 (verified15, nitpick.3) graded this gap on **c6**; the
sibling check found it on **four** cases, and c7 was the one with **no clause table at all** — its
fail-safe was stated entirely as a two-rung ladder. the ladder is the right structure and it stays;
what was absent is the grade a reader compares against c2, c4, c5, c9 and c10.

⚠️ **the edge here is the TEARDOWN, not the object write.** that distinction is the one c10 settled
(verified13/14): a clause grades the moment the actor **meets** the sharp edge, and the distance from
that moment back to its cause is a **latency** measure in its own vocabulary — never a failed clause.

| # | clause | grade |
|---|--------|-------|
| 1 | **fast** | ✅ `delBucket` throws on the **first** `DeleteBucket` call — it does not retry, does not enumerate, does not attempt a purge first |
| 2 | **loud** | ✅ rethrown, never swallowed. `delBucket.ts`'s `.note` records the deliberate choice: *"a non-empty bucket fails loud (by design — we never silently purge objects)"* |
| 3 | **teaches the fix** | 🟢 **it was the one clause that FAILED; RULED GREEN 2026-09-09 by F8.** raw `BucketNotEmpty` is silent on delete markers, on `s3:DeleteObjectVersion`, and on the admin path — so an operator who has just emptied the bucket reads a message that appears to contradict what they observed. the wrap above is the repair, and the council confirmed the richer metadata that carries it. ⚠️ **c7 was the sharpest row in the F8 register** — a declined F8 left this clause ⛔ **red**, where the other four went merely partial. that asymmetry is what made the fulcrum worth an ask |
| 4 | **holds the limit** | ✅ the limit is *empty*, and the operation **holds at it rather than forces past it**. the overshoot on offer — purge the versions so the delete can succeed — is precisely what `delBucket` refuses |
| 5 | 🔴 **drops no data silently** | ✅ **the strongest grade in this table, and it was the reason clause 3 was allowed to sit red while F8 was open.** the failure preserves **every** version and marker. an implementation that scored better on "teaches the fix" by auto-purge would trade an opaque message for irreversible data loss — so the clause that failed was the cheap one, and the clause that held was the expensive one. ⇒ 🔴 **F8's verdict makes that trade moot, and the argument is worth the ink anyway**: it was never *"red is fine"*, it was *"this is the correct clause to owe a fix on"* — and the fix arrived |

⇒ 🔴 **the residual is DIAGNOSTIC LATENCY, and it is what CHARACTERIZES this case rather than a
defect in the fail-safe.** at the edge the failure is fast, loud, and lossless; what it is not is
*near its cause*. the object write that doomed the fixture passed every assertion (`[t3]`), and the
consequence surfaces at a teardown that may be days and several merges away — and, per the narrative,
**for a different person**. ⇒ *this is the same shape as c10's residue, with `person` in place of
`time` as the separator — which is why rung 1 (prevent, at the declaration site) is the load-bearing
rung and rung 2 only softens the arrival.*

## .the `[tn]` timeline

the narrative shows the operator's dead end. the timeline names the claim prose cannot make: that
**every assertion passes** at the moment the damage is done.

```
given  [case7] the acceptance suite, run as `system:ci` with the demo role
  and  a fixture bucket that receives objects in the course of the run (ses writes to it)

  when [t0] the fixture declares versions: { status:'enabled', … } and apply runs
  then  the apply SUCCEEDS
   and  the re-plan reads KEEP
   and  EVERY extant assertion in the suite passes
   and  ⚠️ no plan, no apply, and no assertion renders the hazard —
        the failure is entirely outside what the run observes

  when [t1] an object is written to the bucket mid-run
  then  a versioned object is created

  when [t2] teardown deletes every object, then calls DeleteBucket
  then  each object delete writes a DELETE MARKER rather than removes the object
   and  DeleteBucket fails with BucketNotEmpty
   and  the bucket is NOT deleted

  when [t3] teardown retries after it sets status: 'suspended'
  then  DeleteBucket STILL fails
   and  suspension does not restore the emptiable state (aws, verified)

  when [t4] the operator attempts to remove the versions directly
  then  the demo role is denied — it holds s3:DeleteObject, not s3:DeleteObjectVersion
   and  managed ReadOnlyAccess cannot supply it
   and  the orphan is clearable ONLY with admin credentials

  when [t5] a later run tries to create the fixture again
  then  the bucket name is still taken
   and  ⚠️ s3 bucket names are GLOBAL, so the name is unusable account-wide

  when [t6] — the fail-safe — a versioned fixture is declared object-free (rung 1)
  then  teardown succeeds
   and  the extant `delBucket` guarantee is untouched — objects are never silently purged

  when [t7] — the fail-safe — DeleteBucket fails BucketNotEmpty anyway
  then  the error names VERSIONS and DELETE MARKERS as the contents
   and  it names `s3:DeleteObjectVersion` as the absent grant
   and  it names the admin path, and that the bucket name is global
   and  it does NOT purge objects to make itself pass (rule.forbid.failhide)
```

### what the timeline catches that the narrative does not

- **`[t0]`'s "every assertion passes"** — this is the whole reason the cell is a critipath rather
  than a bug someone would notice. the narrative shows a failure; it cannot show that the failure is
  **invisible to the run that causes it**. the suite reports green, and the damage surfaces in
  teardown, on a later run, or on a different operator's machine.
- **`[t3]`** — prose can state "suspension does not help". only a step can assert it, and it is the
  step most likely to be dropped by an implementer who reasons from the type union rather than from
  aws's object semantics.
- **`[t7]`'s last `and`** — the obvious "fix" for a `BucketNotEmpty` is to purge the bucket
  automatically. that would convert a loud failure into a silent data deletion, which is the exact
  guarantee `delBucket.ts` was written to hold. the fail-safe must teach, never purge.

## .the counterfactual — why this outranks a normal sharp cell

- **frequency** — it fires on the **first** attempt to exercise the wish's headline property on the
  extant fixture, which is the obvious first move, made by someone whose instinct is correct.
- **cost** — every other sharp cell in this space is recoverable by a re-apply, a re-plan, or a
  human who re-runs a command. **this one is not.** the resource cannot be destroyed by the actor
  that created it, its name is permanently consumed in a global namespace, and clearance requires
  credentials the ci actor does not and should not hold.

⇒ `freq × cost` puts it beside c2. it is the only cell in the space where **the tool converges
perfectly and the world is left broken.**
