# case=3 — a versioning retract fails safe

**feel** sharp · **care** critipath · **actor** `consumer` · **cells** 6 (forbidden), 3

invariant **I-1**. aws models a one-way door: a bucket can go `never-set → Enabled → Suspended`,
and can never come back. the consumer will try anyway, because our own type shape invites it.

## .narrative

vlad decides the git-backup bucket does not need version history after all — the grove writes are
already immutable. he opens his wish and turns it off the obvious way:

```ts
-  versions: { status: 'enabled', expire: { after: { days: 30 }, keep: null } },
+  versions: false,
```

🔴 **F16 made that edit EASIER to reach, not harder.** under the flat shape he had to write `null`,
a token that reads as *unset* and carries at least a hint of *"maybe this is a no-op"*. `false` reads
as **off** — an affirmative state — so a consumer who writes it is more confident, not less, that
aws will honour it. ⇒ **a shape that improves legibility can also sharpen the edge it sits next to**,
which is the trade this case now records against **F16**.

he runs plan. **he expects an UPDATE that turns it off**, and that is exactly what he gets:

```
$ npx declastruct plan --wish infra/camp/resources.ts --into .temp/plan.json

🔮 plan changes...

○ ahbode-camp-git-backup
   ├─ ✔ done in 0.43s
   └─ decision [UPDATE]
      - Remote
      + Desired

      - "versions": { "status": "enabled", "expire": { "days": 30 } },
      + "versions": false,
```

so he applies. **the apply is where it stops him:**

```
$ npx declastruct apply --plan .temp/plan.json

🪄  apply changes...

○ [UPDATE] ahbode-camp-git-backup

BadRequestError: s3 offers no way to return a versioned bucket to off; declare status 'suspended' instead

{
  "bucket": "ahbode-camp-git-backup",
  "versionsLive": { "status": "enabled", "expire": { "days": 30 } },
  "versionsDeclared": false,
  "why": "aws models exactly two version states — 'Enabled' and 'Suspended'. once a bucket carries either, it can never return to the never-set state, so no apply could close this.",
  "fix": "declare versions: { status: 'suspended', expire: … } — under it a PUT no longer creates a new version",
  "note": "a suspend does NOT delete extant noncurrent versions, and a DELETE still writes a delete marker; the object itself is not removed. to clear them, keep versions.expire set until they age out."
}
```

🔴 **read the `fix` line against F16 and note what it now costs him.** the flat shape's fix was a
one-token swap — `null` → `'Suspended'`. F16's fix asks for an **object with two keys**, and the
second key is one he just deleted. ⇒ the error MUST name `expire` explicitly, or a consumer who
copies the fix literally writes `versions: { status: 'suspended' }`, hits a *second* compile break,
and reads the first error as incomplete. **an error that teaches a fix must teach the whole fix**
(`rule.require.errors-name-the-fix` — blocker), and F16 widened what "whole" means here.

⚠️ **that output is the real one, and it is NOT what the first pass drew.** the first pass showed a
hand-formatted `🐢 bummer dude` block with `what:/why:/fix:` prose lines. that voice belongs to this
repo's **bash skills**, not to a thrown TypeScript error. `HelpfulError`'s contract is
`(message: string, metadata?)` and it *"adds metadata to the message, serialized"* — so a throw
emits **one message line plus serialized metadata**, exactly as above. see defect 26.

vlad reads it, says *"ah — right, that's an s3 fact, not a declastruct one"*, writes the suspended
object the `fix` line spelled out, and re-plans:

```
○ ahbode-camp-git-backup
   └─ decision [UPDATE]
      - "versions": { "status": "enabled",   "expire": { "days": 30 } },
      + "versions": { "status": "suspended", "expire": { "days": 30 } },
```

🟢 **and F16 gave him something the flat shape could not: the diff shows he KEPT the expiry.** under
`versions: 'Enabled' -> 'Suspended'` the noncurrent-expiry field sat elsewhere in the object and did
not move, so the diff was silent on whether his aged-out versions would still be swept. here the two
keys travel together, so **the one line he reads answers both questions** — the door is shut, and
the sweep continues.

it applies. the re-plan reads `[KEEP]` and `🎉 everything is in sync!`.

### ⚠️ the rejection lands at APPLY, not at plan — corrected by the r1 self-review

the first pass rendered this rejection at **plan** and claimed that as the fail-fast win. that is
not implementable, and would break a blocker rule if forced:

- **declastruct's plan has no hook for it.** `planChanges` calls `dao.get.one.byUnique` then
  `computeChange`, and `computeChange` (`computeChange.js:24-51`) only compares serialized forms →
  CREATE / DESTROY / KEEP / UPDATE. the `DeclastructDao` contract
  (`DeclastructDao.d.ts:12-94`) carries exactly `dobj`, `get.*`, and `set.*` — **there is no
  validation hook** that sees desired and remote together at plan time.
- **the one loophole is forbidden.** `dao.get.one.byUnique(resource, …)` is handed the whole desired
  object at runtime, so a `get` *could* peek at `desired.versions` and throw. that is precisely
  what `rule.forbid.plan-fail-on-apply-guided-prereq` forbids as a **blocker**: *"a `get` must NEVER
  hard-throw on an unmet precondition that the resource's own `set` is designed to guide or fix."*
  the guided `set` is exactly the sanctioned home for this error.
- **the home is precise, not vague.** `applyChange.js:31-40` routes UPDATE to `dao.set.upsert`, and
  `DeclaredAwsS3BucketDao.ts:34-36` wires that to `setS3Bucket({ upsert })`. so the guard is the
  first statement of `setS3Bucket`'s upsert path, where both the declared `false` and the live
  `'Enabled'` are in hand.

**and the plan's UPDATE is not permadrift.** permadrift is an UPDATE plus an apply that reports
success while it changes no state. this is an UPDATE plus an apply that **refuses, loudly, with the
fix**. the plan is honest — vlad really did declare a change — and the apply is where a transition
aws does not model gets named.

**the edge did not cut him.** he spent thirty seconds and learned a real fact about s3. the
alternative — the one this case exists to prevent — is a plan that reads `UPDATE versioning
'Enabled' -> null` forever, an apply that reports success while it writes no change, and vlad in a
console tab an hour later trying to work out which of the two is lying.

### ⚠️ what `'Suspended'` actually means — fetched, and narrower than the first pass implied

the fix line originally read *"it halts new versions"*. aws's `API_DeleteObject.html`, fetched,
shows that is true only for the **write** path:

| under `'Suspended'` | aws's behaviour |
|---------------------|-----------------|
| a **PUT** | stores the object with a `null` versionId — so no new version accrues. ✅ the claim holds |
| a **DELETE** | *"removes the object that has a null `versionId`, if there is one, **and inserts a delete marker** … If there isn't an object with a null `versionId`, and all versions of the object have a `versionId`, Amazon S3 **does not remove the object**"* |

⇒ so `'Suspended'` is **not** "versioning off". it halts new versions on write and changes the
delete semantics not at all. the message now says so, because a consumer who reads "halts new
versions" and then tries to empty the bucket will be surprised — and per `rule.forbid.surprises`
that surprise is ours to prevent, in the very error that recommends the state.

🔴 **and it has a consequence beyond the consumer: `'Suspended'` does not restore a safe teardown.**
the natural escape from the test-harness hazard — *"suspend it before del"* — fails for exactly the
reason in the table's second row. see the yield's *"a versioned test bucket must never receive an
object"* constraint. **the one-way door is one-way for the teardown path too**, not merely for the
declared state — which is the sharpest available statement of invariant I-1.

## .the fail-safe proof

per `define.experience` a sharp critipath must prove the edge fails **fast**, **loud**, and
**teaches the fix** — and the census rubric grades **five** clauses, so all five are graded here.

🔴 **clauses 4 and 5 were added at verified21.** peer review r2 (verified15, nitpick.3) graded the
same gap on **c6**; the sibling check found it on **four** cases — c3, c6, c7, c8 — while c2, c4,
c5, c9 and c10 already graded five. ⚠️ **and on this case the two added clauses are the strongest
grades in the table**, because a retract is exactly the operation whose failure mode is silent data
loss.

| # | clause | grade |
|---|--------|-------|
| 1 | **fast** | ✅ caught at the **top of the `set`**, before it issues a single s3 write for this bucket — so the bucket is never left half-reconciled. it is not as early as plan, and it cannot be: see the ⚠️ above (`rule.require.failfast`, `rule.forbid.plan-fail-on-apply-guided-prereq`) |
| 2 | **loud** | ✅ a `BadRequestError` — the class this repo uses for *"logic has successfully rejected a request"*. never swallowed, never degraded to a no-op KEEP (`rule.require.failloud`, `rule.forbid.failhide`) |
| 3 | **teaches the fix** | ✅ names the legal alternative `status: 'suspended'`, shows the exact line to write, and adds the consequence the consumer would otherwise discover later — a suspend does not delete extant versions (ergonomist `rule.require.errors-name-the-fix`). 🔴 **F16 raised this clause's bar**: the fix is an object now, so the message must carry `expire` too — a fix that names only `status` compiles to a second break |
| 4 | 🔴 **holds the limit** | ✅ **this case IS the limit, so the clause is the load-bearing one.** aws's floor is `'Suspended'`; `false` sits below it and does not exist on a bucket that was ever versioned. the rejection **holds at the floor** — the remote keeps its extant value, the wish is refused, and the consumer is handed the floor's name. the failure mode this bars is an overshoot: a retract silently reinterpreted as a suspend, which would ship a state the consumer never declared. ⚠️ **F16 did not move this floor, and could not** — the one-way door is aws's, not our shape's |
| 5 | 🔴 **drops no data silently** | ✅ **on both readings, and they are different guarantees.** (i) *at the edge*: the throw precedes every s3 write, so no version, no marker, and no config is touched — the refusal costs zero data. (ii) *at the fix*: the error states outright that `'Suspended'` **retains extant versions**, so a consumer who takes the taught fix does not later discover a history they had assumed was cleared. ⇒ clause 3 teaches the fix; clause 5 is why that fix does not itself become a silent loss |

**caller-must-fix, not server-must-fix — and the class this repo has for that is `BadRequestError`.**
the fix is a change to vlad's wish, so the throw must say "do not retry; a human must edit the
declaration". `BadRequestError`'s own doc states the semantic exactly: *"used to explicitly declare
that your logic has successfully rejected a request … an apparent caller error"*. the sibling
`UnexpectedCodePathError` is the wrong pick — this path is entirely reachable by a valid wish.

⚠️ **the first pass said `ConstraintError` (exit 2) vs `MalfunctionError` (exit 1), and both halves
were wrong.** `helpful-errors` — the package every `src/` throw imports — exports exactly
`HelpfulError`, `UnexpectedCodePathError`, `BadRequestError`, `getError`, `withHelpfulError`. it has
**no `ConstraintError`, no `MalfunctionError`, and no exit codes at all**. those two classes come
from `test-fns`, a **test** library, so they could not be used by a domain operation even if the
distinction were wanted. see defect 26.

## .the `[tn]` timeline

the narrative shows the recovery. the timeline pins where the rejection fires and what it must
*not* do — the two parts prose glosses.

```
given  [case3] a bucket whose live version state is 'Enabled'

  when [t0] the wish declares versions: false and plan runs
  then  the decision is UPDATE, `{status:'enabled',…} -> false`
   and  the plan does NOT read KEEP  (a silent no-op would hide what vlad asked for)
   and  the plan does NOT throw     (rule.forbid.plan-fail-on-apply-guided-prereq)

  when [t0b] apply runs that UPDATE (dao.set.upsert -> setS3Bucket({ upsert }))
  then  the set FAILS with a BadRequestError, before its first s3 write
   and  the message names the extant state, the declared state, and 'suspended'
   and  🔴 the fix line names BOTH keys of the suspended object — status AND
        expire — since F16 made the fix an object rather than a token, and a
        half-taught fix costs a second compile break
        (rule.require.errors-name-the-fix — blocker)
   and  the bucket is left EXACTLY as it was — no partial reconcile
   and  the apply does NOT report success having written no change
        (THAT silent no-op, not the UPDATE itself, is the permadrift)

  when [t1] the wish declares versions: { status:'suspended', expire:{days:30} }
  then  the decision is UPDATE, and the diff shows status change with expire HELD

  when [t2] apply runs
  then  `PutBucketVersioning{Status:'Suspended'}` is issued
   and  🔴 NO lifecycle put is issued — `expire` did not change, and F16's one
        object spans TWO aws calls, so a naive "the object changed, write it
        all" would issue a redundant PutBucketLifecycleConfiguration
        (F16 sub-call 2 — the per-key write split, graded at execution)
   and  a re-plan reads KEEP

  when [t3] the wish declares versions: false on a bucket that is 'Suspended'
  then  apply FAILS the same way — 'Suspended' is also unreachable-from
        (the one-way door has no exit at either versioned state)

  when [t4] the wish declares versions: false on a bucket that was NEVER versioned
  then  the decision is KEEP  (cell 4 — this is the legal `false`, and it must
        stay legal; F16 renamed the token and did NOT narrow the cell)
```

### what the timeline catches that the narrative does not

- **`[t0]` / `[t0b]`'s split** — the sharpest line in this case, and the one the first pass got
  backwards. the plan reading **UPDATE is correct**; what must never happen is the *apply* that
  reports success while it writes no change. so the forbidden behaviours are a silent KEEP at plan
  (which quietly discards what vlad asked for) and a silent success at apply (the actual
  permadrift). an UPDATE followed by a loud refusal is the **right** shape, and prose reads the two
  as one blurred "it should reject".
- **`[t3]`** — the narrative only covers `Enabled`. `Suspended → null` is the same door and the
  same rejection; without the row it would be easy to guard only the first.
- **`[t4]`** — the crucial boundary. the guard must fire on *live-is-versioned*, never on
  *declared-is-null*. a guard written the second way would break every unversioned bucket in
  existence, including marina's mail store in case=2.
