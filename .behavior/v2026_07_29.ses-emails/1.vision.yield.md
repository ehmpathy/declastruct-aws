# 1.vision — provision send+receive email infra via declastruct-aws

> wish: `.behavior/v2026_07_29.ses-emails/0.wish.md`
> "enable folks to provision the resources required to send and read emails"

---

## .the generalization

the peer's handoff describes ONE instance — a robot mailbox `robot@bot.ehmpath.com`
backed by an s3 store, authed via `AWS_PROFILE`. the wish asks us to **generalize** that
usecase and to **center subdomains** (`mail.ehmpath.com`), with `demo.ehmpathy.com` as the
test domain.

so the vision is NOT "declare a robot mailbox." it is:

> **declare the reusable aws primitives that let any consumer stand up send + receive
> email for a mail (sub)domain they own — idempotently, reproducibly, via `declastruct
> apply` — the same way declastruct-aws already declares vpc, ec2, iam, ssm, and budgets.**

the robot mailbox is then just one arrangement of those primitives. so is a support inbox,
a notifications sender, a catch-all archive. the primitives are the product; the mailbox is
a recipe.

---

## .decisions locked with the wisher (2026-07-29)

the four fulcrums are settled — these are no longer open:

1. **robot identity = a dedicated declared role.** the send/read grant attaches (via inline
   policy) to a purpose-built `DeclaredAwsIamRole` the robot assumes — NOT the ambient
   SSO-managed role. stable, least-privilege, does not fight SSO provision.
2. **send-from scope = subdomain grain.** the `ses:SendRawEmail` grant is scoped to
   `*@demo.ehmpathy.com` (the whole subdomain), not a single hard-coded address.
3. **verified identities are ALWAYS declared.** the domain, the sandbox test recipient, and
   the send-from address are all declared as `DeclaredAwsSesEmailIdentity` resources — never
   a manual verify. see the naming decision below: AWS models domain AND email identities as
   ONE resource (`AWS::SES::EmailIdentity`), so there is a single declared noun, not two.
4. **s3 is fully in scope; lifecycle is an s3 config, selectable across THREE modes.** the
   S3 resources (`DeclaredAwsS3Bucket`, `DeclaredAwsS3BucketPolicy`) are declared here, and
   the bucket's object lifecycle is modeled **as an s3 bucket config** — a
   `lifecycle` field on `DeclaredAwsS3Bucket` (aws PutBucketLifecycleConfiguration), a
   **per-consumer selection** among:
   - **persist** — keep every object in Standard forever (no rule)
   - **progressive glacier archival (explicit staircase)** — a declared transition schedule
     that steps objects down the cold classes over time (Standard → Standard-IA →
     `GLACIER_IR` / `GLACIER` → `DEEP_ARCHIVE` at consumer-set day thresholds), optionally
     expiring at the end. this is the "glacialize docs over time" ask — a deterministic,
     declared staircase the consumer controls.
   - **aws auto-tier** — hand the cold/warm decision to AWS: one lifecycle transition to the
     `INTELLIGENT_TIERING` storage class, and AWS moves objects between access classes by
     observed access pattern. no day thresholds to declare.
   the explicit staircase and the auto-tier are **alternatives** (pick one per bucket); the
   `DeclaredAwsS3Bucket` lifecycle config must model both shapes.

5. **resource names MIRROR aws (verified against CloudFormation).** the declared nouns match
   AWS's own resource types 1:1 — with ONE correction from the first draft:
   - `DeclaredAwsS3Bucket` = `AWS::S3::Bucket`, `DeclaredAwsS3BucketPolicy` =
     `AWS::S3::BucketPolicy` ✅
   - `DeclaredAwsSesReceiptRuleSet` = `AWS::SES::ReceiptRuleSet`,
     `DeclaredAwsSesReceiptRule` = `AWS::SES::ReceiptRule` ✅
   - **correction**: AWS has NO `DomainIdentity` resource. since mid-2022 there is a single
     `AWS::SES::EmailIdentity` whose identity value is EITHER a domain OR an address (a
     domain-valued one emits DKIM tokens; an address-valued one is a plain verify). so the
     first draft's `DeclaredAwsSesDomainIdentity` + `DeclaredAwsSesEmailIdentity` split
     collapses to ONE `DeclaredAwsSesEmailIdentity` (`identity` = domain | email), to honor
     `rule.require.ubiqlang`.

## the outcome world

### day-in-the-life

a consumer (a human, or a downstream repo like the gatherer role) wants a mail domain that
can receive to s3 and send out. they open a `resources.mail.ts` file and declare:

```ts
keyrack.source({ env: 'test', owner: 'ehmpath', mode: 'lenient' });

// aws models domain AND email identities as ONE resource — identity = domain | email
const identity = DeclaredAwsSesEmailIdentity.as({
  identity: 'demo.ehmpathy.com',      // a DOMAIN value -> emits dkim tokens for dns
  dkim: 'enabled',
  tags: { managedBy: 'declastruct', purpose: 'mail' },
});

const store = DeclaredAwsS3Bucket.as({
  name: 'ehmpathy-mail-inbound-demo',  // globally-unique
  // lifecycle is an s3 config; pick ONE mode:
  //   persist:   lifecycle: null
  //   staircase: lifecycle: { transitions: [{ afterDays: 30, class: 'GLACIER_IR' },
  //                                          { afterDays: 180, class: 'DEEP_ARCHIVE' }],
  //                           expireAfterDays: 3650 }
  //   auto-tier: lifecycle: { transitions: [{ afterDays: 0, class: 'INTELLIGENT_TIERING' }] }
  lifecycle: { transitions: [{ afterDays: 30, class: 'GLACIER_IR' },
                             { afterDays: 180, class: 'DEEP_ARCHIVE' }] },
  tags: { managedBy: 'declastruct', purpose: 'mail' },
});

const storePolicy = DeclaredAwsS3BucketPolicy.as({
  bucket: RefByUnique.as<typeof DeclaredAwsS3Bucket>(store),
  // allow SES (this account only) to PutObject — reuses the extant IAM policy dobjs
  document: { statements: [ /* ses.amazonaws.com -> s3:PutObject, SourceAccount cond */ ] },
});

const ruleSet = DeclaredAwsSesReceiptRuleSet.as({
  name: 'ehmpathy-mail-inbound',
  status: 'active',                    // one active set per region
});

const rule = DeclaredAwsSesReceiptRule.as({
  ruleSet: RefByUnique.as<typeof DeclaredAwsSesReceiptRuleSet>(ruleSet),
  name: 'to-s3',
  recipients: ['inbox@demo.ehmpathy.com'],
  actions: [{ s3: { bucket: RefByUnique.as(store), prefix: 'inbound/' } }],
});

// the robot's own role + a least-privilege grant scoped to the subdomain
const robotRole = DeclaredAwsIamRole.as({
  name: 'ehmpathy-mail-robot',
  policies: [{ effect: 'Allow', principal: { service: 'ec2.amazonaws.com' }, action: 'sts:AssumeRole' }],
  tags: { managedBy: 'declastruct', purpose: 'mail' },
});
const robotGrant = DeclaredAwsIamRolePolicyAttachedInline.as({
  name: 'mail-send-read',
  role: RefByUnique.as<typeof DeclaredAwsIamRole>(robotRole),
  document: { statements: [
    { effect: 'Allow', action: 's3:GetObject', resource: `arn:aws:s3:::${store.name}/inbound/*` },
    { effect: 'Allow', action: 'ses:SendRawEmail', resource: '*',
      // scope the send to the whole subdomain, not one address (decision 2)
      condition: { StringLike: { 'ses:FromAddress': '*@demo.ehmpathy.com' } } },
  ] },
});

// verified addresses are always declared, never a manual verify (decision 3)
// — the SAME EmailIdentity resource, now with an EMAIL value instead of a domain
const sendFrom = DeclaredAwsSesEmailIdentity.as({ identity: 'robot@demo.ehmpathy.com' });
const testRecipient = DeclaredAwsSesEmailIdentity.as({ identity: 'qa@demo.ehmpathy.com' });
```

then:

```sh
rhx keyrack unlock --owner ehmpath --env test
npx declastruct plan  --wish resources.mail.ts --into .temp/plan.json
npx declastruct apply --plan .temp/plan.json
```

the apply creates the aws side and **prints the exact cloudflare DNS records to paste**
(mx, `_amazonses` verification TXT, 3 dkim CNAMEs, spf, dmarc), resolved from the applied
domain-valued `DeclaredAwsSesEmailIdentity`. a human pastes those once. thereafter, `plan` shows
`KEEP` for every resource, and mail flows: sender → mx → ses receipt rule → s3, and
`SendRawEmail` → recipient.

### before / after

| | before (console, by hand) | after (declastruct) |
|---|---|---|
| verify domain | click through SES console, copy tokens | `apply` emits the tokens in its output |
| dkim | enable per-domain, copy 3 CNAMEs | emitted alongside verification |
| s3 store + policy | create bucket, hand-write the `SourceAccount` bucket policy, hope SES's test-put passes | declared; policy reuses the extant IAM policy dobjs, applies before the rule |
| receipt route | create rule set, remember to **set-active**, add rule | declared; set-active is explicit + guarded |
| reproduce in a 2nd account | re-do every click, undocumented | re-run the same wish |
| drift | invisible until mail silently stops | `plan` shows it |

### the "aha"

the value clicks the moment `apply` **prints the DNS records to paste** — the one step
declastruct genuinely cannot do (cloudflare is a different provider, owned by a human) is
handed to the human as copy-paste-ready output, and *all else* is declared. the consumer
never opens the SES console. re-run is a no-op `KEEP`, so the whole mail stack becomes as
reproducible as the vpc stack already is.

## user experience

### usecases / goals

- **provision a mail domain** — verify + dkim-sign a (sub)domain for send + receive
- **receive to a store** — route inbound mail for chosen recipients into an s3 prefix as
  raw rfc822 (a downstream adapter reads + parses it; out of scope for this wish)
- **authorize send** — grant a principal `ses:SendRawEmail` so it can respond
- **least-privilege the robot** — attach exactly the s3-read + ses-send grant, no more
- **measure "how easy is it"** — the peer's real goal: prove a domain we own can be stood
  up + authed with `AWS_PROFILE` alone, no oauth, no token upkeep

### contract inputs & outputs

inputs (desired state the consumer declares):

| resource (= aws type) | @unique | consumer sets | notes |
|---|---|---|---|
| `DeclaredAwsSesEmailIdentity` (`AWS::SES::EmailIdentity`) | `identity` | `identity` (a domain OR an email), dkim on/off, tags | ONE resource for both — a domain value emits dkim + needs dns; an email value is a plain verify |
| `DeclaredAwsS3Bucket` (`AWS::S3::Bucket`) | `name` | name (globally unique), **lifecycle config (persist \| staircase \| auto-tier)**, tags | the inbound store; lifecycle is an s3 bucket config, per-consumer choice |
| `DeclaredAwsS3BucketPolicy` (`AWS::S3::BucketPolicy`) | `bucket` | policy document | reuses `DeclaredAwsIamPolicyDocument`/`Statement` |
| `DeclaredAwsSesReceiptRuleSet` (`AWS::SES::ReceiptRuleSet`) | `name` | name, active status | one active set per region |
| `DeclaredAwsSesReceiptRule` (`AWS::SES::ReceiptRule`) | `ruleSet`+`name` | recipients, ordered `actions[]` from the **full native SES union** (all 8: `s3` \| `sns` \| `lambda` \| `bounce` \| `stop` \| `addHeader` \| `workmail` \| `connect`) | the route rule; **forward-to-address and Slack are NOT native actions** — both ride on a `lambda` action (a Lambda reads the s3 message + `ses:SendRawEmail` to forward, or posts a Slack webhook). the whole union is modeled for a faithful AWS mirror; `workmail`/`connect` are niche but included for parity; the Lambda body is a downstream consumer concern, not this wish. |
| `DeclaredAwsIamRole` + `DeclaredAwsIamRolePolicyAttachedInline` | `name` | the robot's assumable role + its least-privilege grant | **dedicated role (decision 1)** — not the ambient SSO role; grant scoped to `*@demo.ehmpathy.com` (decision 2) |
| `DeclaredAwsSesConfigurationSet` (`AWS::SES::ConfigurationSet`) | `name` | name, tags | groups sent mail for open + feedback event capture |
| `DeclaredAwsSesConfigurationSetEventDestination` (`AWS::SES::ConfigurationSetEventDestination`) | `configurationSet`+`name` | event types (send/reject/bounce/complaint/delivery/open/click), sink (cloudwatch \| sns) | sns sink → a `DeclaredAwsSnsTopic` (net-new); cloudwatch sink → no new resource |

the **same** `DeclaredAwsSesEmailIdentity` serves the domain, the send-from address, and the
sandbox test recipient — the identity value discriminates. always declared (decision 3),
never a manual verify.

outputs (`@readonly`, resolved from aws — the reason to declare an identity at all):

| resource | emits (when identity = domain) | the human uses it to |
|---|---|---|
| `DeclaredAwsSesEmailIdentity` | `dkimTokens[3]`, `verificationStatus`, `dkimStatus` (a domain value); `verificationStatus` only (an email value) | fill the cloudflare TXT + CNAME records; know when ready |

the send + auth-status paths:

- least-privilege grant → an inline policy (`DeclaredAwsIamRolePolicyAttachedInline`, already
  writable) on a **dedicated declared role** the robot assumes — NOT the ambient SSO role
  (decision 1). the grant body (built from `DeclaredAwsIamPolicyStatement`) scopes
  `ses:SendRawEmail` to the **subdomain grain** `*@demo.ehmpathy.com` (decision 2), not a
  single address
- auth-status → `sts:GetCallerIdentity` (already how the provider reads the account)

### timeline

```
declare  ─▶ apply identity ─▶ apply bucket + policy ─▶ apply rule-set ─▶ apply rule ─▶ apply iam grant
                │                                                                          │
        emits tokens ──▶ HUMAN pastes DNS in cloudflare (once) ──▶ dns propagates          │
                                                                        │                  ▼
                                              receive: sender ▶ mx ▶ rule ▶ s3      send: SendRawEmail ▶ recipient
```

apply order matters and is the **declared array order** (declastruct does no topological
sort): identity → bucket → bucketPolicy → ruleSet → rule → iam. the rule must be last of
the ses chain because SES does a live test-put against the bucket at rule-create time, so
the bucket + its policy must already exist.

## mental model

### how a user describes it to a friend

> "it's like terraform for an email inbox. i write down the domain, a bucket, and a route
> rule, run apply, and it tells me the DNS to paste. after that, mail to my domain lands in
> s3 and i can send from it — all with my aws profile, no gmail oauth dance."

### analogies

- **a po box you declare**: the identity is the box's registration, the receipt rule is the
  sort slip that says "put mail for these addresses into this bin (s3 prefix)."
- **the vpc precedent**: exactly as `resources.vpc.ts` already declares subnets + route
  tables + a nat, `resources.mail.ts` declares an identity + store + receipt rule. same
  get/set/KEEP rhythm.

### terms — theirs vs ours

| they say | we say (ubiqlang / aws) |
|---|---|
| "the inbox / mailbox" | domain identity + receipt rule + s3 prefix |
| "verify the domain" | `DeclaredAwsSesEmailIdentity` with a domain value (`AWS::SES::EmailIdentity`) |
| "the route rule" | `DeclaredAwsSesReceiptRule` |
| "the mail bucket" | `DeclaredAwsS3Bucket` + `DeclaredAwsS3BucketPolicy` |
| "let it send" | inline `ses:SendRawEmail` grant via `DeclaredAwsIamRolePolicyAttachedInline` |
| "the DNS stuff" | the `@readonly` tokens the identity emits, pasted into cloudflare |

we keep aws's own nouns (`DeclaredAws{Service}{Resource}`, service prefix `Ses`/`S3`) so the
family autocompletes together and mirrors aws docs — per
`rule.require.symmetry-with-peer-resources`.

## evaluation

### how well it solves the goals

- **provision send+receive**: fully — the new resources (ses domain identity, ses email
  identity, s3 bucket + policy, ses receipt rule-set + rule) plus a dedicated iam role + its
  inline grant cover the whole aws side; the only non-declarative step (cloudflare DNS) is
  inherent to a cross-provider boundary and is handed over as copy-paste output.
- **generalize**: yes — no field hard-codes the robot; `demo.ehmpathy.com`, a support
  inbox, or a notifications sender are all just different field values.
- **subdomain-first**: yes — `domain` is any label; a subdomain keeps the apex mx untouched
  (isolated blast radius), which is the wish's stated preference.

### pros

- reuses the proven declastruct get/set/KEEP pattern and the extant IAM policy dobjs
- idempotent + reproducible; drift is visible in `plan`
- least-privilege via inline policy — sidesteps the read-only `DeclaredAwsIamPolicy` dao
  entirely (no need to make it writable)
- dogfoods in `provision/aws.infra/account=demo/` AND covers via acceptance, per
  `rule.require.dao-and-acceptance-per-declared-resource`

### cons / tradeoffs

- **cross-provider seam**: declastruct owns aws; a human owns cloudflare DNS. the flow is
  not one-command end-to-end. we mitigate with emitted copy-paste records, but the seam
  is real (an eventual `declastruct-cloudflare` provider could close it — out of scope).
- **classic SES v1 api**: receipt rules live only in `@aws-sdk/client-ses` (v1). the newer
  "SES Mail Manager" is a separate service. we pin classic receipt rules (still fully
  supported) — see open questions.
- **region-locked receive**: SES inbound works only in a subset of regions; the provider's
  resolved region must be one of them or rule-create fails.

### edge cases → pit of success

| edge case | how the contract keeps you safe |
|---|---|
| domain not yet verified (DNS not pasted) | `get` **degrades** to `verificationStatus: 'unresolved'` — never a plan-time throw (`rule.forbid.plan-fail-on-apply-guided-prereq`). apply re-emits the tokens as guidance. |
| another active receipt rule set already exists | set-active must **fail loud**, not silently steal the one active slot (`rule.forbid.silent-resource-theft`) — a foreign active set forces human disambiguation. |
| provider region is not SES-inbound-capable | `set` fails loud early, names the supported regions (`rule.require.errors-name-the-fix`), rather than a cryptic SES error deep in rule-create. |
| bucket policy absent/wrong `SourceAccount` | rule declared AFTER bucket+policy; SES's create-time test-put verifies write — if it fails, apply stops before a half-wired rule. |
| s3 bucket name already taken globally | `CreateBucket` conflict → fail loud on the name, not a silent adopt of another owner's bucket. |
| inbound message exceeds SES's receive size cap (40 MB, or >10 attachments) | out of our contract's hands — SES bounces the oversized message before the receipt rule fires, so it never reaches s3. the cap is a verified 40 MB default (cited below), not a silent drop; a size-sensitive consumer should know large attachments will not arrive. a stricter cap needs Mail Manager traffic policy, out of v1 scope. |
| SES sandbox (send only to verified) | disclosed, not hidden: v1 test verifies one recipient; production access is a one-time aws support step, flagged — not a declastruct resource. the recipient's verification may itself be a declared `DeclaredAwsSesEmailIdentity` (see open questions) so the test's precondition is reproducible, not a manual out-of-band click. |
| identity cannot reach `verified` in acceptance (no live DNS in `demo.ehmpathy.com`) | the acceptance bar for a domain-valued `DeclaredAwsSesEmailIdentity` is "created + emits tokens + `verificationStatus: unresolved` → KEEP" — NOT "verified". the `get` must treat `unresolved` as a normal KEEP state, so acceptance passes before any human pastes DNS (same spirit as the `ec2SshKeyAuthorized` `.seed` split). full receive e2e (mx→s3) needs live DNS + a real inbound message, so it is an integration/manual measurement, not an acceptance assertion. |
| re-apply | every resource converges to `KEEP` (findsert finds, upsert reconciles) — `rule.require.guaranteed-idempotency`. |

## complete resource inventory — end to end (dogfood-ready)

research (cited below) confirms the FULL set of pieces across both paths — receive
(mx → ses → s3) and send (`SendRawEmail` → recipient). every part is one of: a declared
`DeclaredAws*` resource, a human-pasted DNS record (emitted by apply), or a deliberate
omission with a reason. no part outside these tables is needed for send + receive to work.

### the declared aws resources (what `declastruct apply` creates)

| # | resource | aws type | why required |
|---|---|---|---|
| 1 | `DeclaredAwsSesEmailIdentity` (domain value) | `AWS::SES::EmailIdentity` | verify + dkim-sign the (sub)domain; emits tokens |
| 2 | `DeclaredAwsS3Bucket` | `AWS::S3::Bucket` | the inbound store (+ lifecycle config) |
| 3 | `DeclaredAwsS3BucketPolicy` | `AWS::S3::BucketPolicy` | let `ses.amazonaws.com` PutObject into the store |
| 4 | `DeclaredAwsSesReceiptRuleSet` | `AWS::SES::ReceiptRuleSet` | the rule container; one active set per region |
| 5 | `DeclaredAwsSesReceiptRule` | `AWS::SES::ReceiptRule` | route chosen recipients → s3 prefix |
| 6 | `DeclaredAwsIamRole` | `AWS::IAM::Role` | the robot's assumable identity |
| 7 | `DeclaredAwsIamRolePolicyAttachedInline` | inline policy on the role | least-privilege s3-read + ses-send grant |
| 8 | `DeclaredAwsSesEmailIdentity` (email values) | `AWS::SES::EmailIdentity` | verify the send-from + sandbox test recipient |
| 9 | `DeclaredAwsSesConfigurationSet` | `AWS::SES::ConfigurationSet` | groups sent mail so open + feedback events can be captured |
| 10 | `DeclaredAwsSesConfigurationSetEventDestination` | `AWS::SES::ConfigurationSetEventDestination` | route send/reject/bounce/complaint/delivery/open/click events to a sink |
| 11 | `DeclaredAwsSnsTopic` (net-new, if SNS sink) | `AWS::SNS::Topic` | the event sink a consumer subscribes to; net-new — no SNS resource in the repo yet |

rows 1 and 8 are the SAME resource type at different identity values. the config set +
event destination (9, 10) turn on open + feedback event capture (per the svc-notifications
parity ask below). row 11 is only needed when the event sink is SNS — a CloudWatch sink adds
no new resource. so the type surface is **9 nouns** (2 reuse the extant IAM family) — 10 with
the SNS sink — applied as ~11 instances for a full send + receive + events mailbox.

### the human-pasted DNS (emitted by apply — the cloudflare seam)

| record | for | path |
|---|---|---|
| MX `10 inbound-smtp.<region>.amazonaws.com` on `<domain>` | route inbound to SES | receive |
| TXT `_amazonses.<domain>` = verification token | domain ownership | both |
| 3× CNAME `<token>._domainkey.<domain>` | easy-dkim (auto-rotate ~90d) | both |
| TXT `<domain>` = `v=spf1 include:amazonses.com ~all` | authorize SES to send | send |
| **MX + TXT SPF on the custom MAIL FROM subdomain** | **SPF/DMARC alignment** | **send** |
| TXT `_dmarc.<domain>` (optional) | dmarc policy | send |

### the deliberate omissions (proven optional, not gaps)

| omitted | why safe to skip for v1 |
|---|---|
| SNS topic on the receipt rule's s3 action (receive-path notify) | the adapter polls s3; the receive-path `S3Action` notify is optional (note: the SEND-path event sink IS in scope — rows 9-11) |
| KMS key on the s3 action | SES uses the default `aws/ses` key or none; a CMK is an opt-in |
| custom open/click redirect domain (the config set's redirect-domain option) | open + click events work off SES's default redirect domain; a custom one is an enhancement (svc-notifications left it as a TODO) |
| Mail Manager traffic policy | only needed to cap message size BELOW the 40 MB default |

### two subtle correctness details the research surfaced

1. **the bucket policy's `aws:SourceArn` must be the RECEIPT RULE arn, not the rule-set arn**
   — `arn:aws:ses:<region>:<account>:receipt-rule-set/<ruleSetName>:receipt-rule/<ruleName>`.
   every part is declared, so the ARN is deterministic and the policy can name it before the
   rule applies — but the policy body must build the RULE arn (with `aws:SourceAccount` as a
   second condition), or SES's create-time test-put fails Access Denied. this sharpens the
   `DeclaredAwsS3BucketPolicy` shape.
2. **a custom MAIL FROM domain is required for strict SPF/DMARC alignment** — without it SPF
   authenticates against `amazonses.com`, so a strict DMARC receiver may reject the robot's
   mail. modeled as an optional `mailFrom` field on `DeclaredAwsSesEmailIdentity` (aws
   `MailFromAttributes`: `MailFromDomain` + `BehaviorOnMxFailure`), which adds the MAIL FROM
   MX + SPF TXT records above. optional for the v1 "how easy is it" pass; required before the
   robot sends to strict external receivers.

### parity target — replace `ahbode/svc-notifications` SES terraform

svc-notifications declares its SES stack in terraform (`provision/aws/product/ses.*.tf` +
`s3.tf`, verified on `origin/main`). a stated goal is that this vision **totally replaces**
that terraform. it does — every resource they declare maps to a declared noun here, and the
vision closes two gaps their terraform left open:

| svc-notifications terraform | this vision's declared noun | note |
|---|---|---|
| `aws_ses_configuration_set` | `DeclaredAwsSesConfigurationSet` | 1:1 |
| `aws_ses_event_destination` (cloudwatch) | `DeclaredAwsSesConfigurationSetEventDestination` (cloudwatch sink) | their event set: send/reject/bounce/complaint/delivery/open/click |
| `aws_ses_event_destination` (sns) | `DeclaredAwsSesConfigurationSetEventDestination` (sns sink) | pulls in `DeclaredAwsSnsTopic` — net-new noun |
| `aws_ses_receipt_rule_set` | `DeclaredAwsSesReceiptRuleSet` | 1:1 |
| `aws_ses_active_receipt_rule_set` | the `status: 'active'` field on `DeclaredAwsSesReceiptRuleSet` | terraform splits set-active into its own resource; we model it as a field (guarded per `rule.forbid.silent-resource-theft`) |
| `aws_ses_receipt_rule` (s3 + sns action) | `DeclaredAwsSesReceiptRule` | s3 action in scope; the receive-notify sns action optional |
| `aws_s3_bucket` (received_emails_bucket) | `DeclaredAwsS3Bucket` | + our lifecycle config (persist/staircase/auto-tier) — theirs declares none |
| `aws_s3_bucket_policy` | `DeclaredAwsS3BucketPolicy` | **we harden it**: theirs grants `ses.amazonaws.com` PutObject with NO `aws:SourceArn`/`aws:SourceAccount` condition — we add both (current AWS guidance) |
| (none — manual, their TODO AHB-153) | `DeclaredAwsSesEmailIdentity` (domain + dkim + mail-from) | **we close the gap**: their terraform declares NO domain identity, dkim, or mail-from — by hand today |
| `aws_sns_topic` ×2 | `DeclaredAwsSnsTopic` (net-new) | the send-event sink + the receive-notify topic |

so the vision is a strict **superset** of their terraform: full parity on the config set,
event destinations, receipt chain, and bucket — PLUS the domain identity + dkim + mail-from
they never automated, a hardened bucket policy, and a per-consumer lifecycle. the one genuine
net-new dependency this parity pulls in is `DeclaredAwsSnsTopic` (no SNS resource in the repo
yet) — needed for the SNS event sink and the receive-notify action.

## open questions & assumptions

### assumptions made

1. **classic SES receipt rules** (`@aws-sdk/client-ses` v1) are the receive mechanism — not
   the newer SES Mail Manager. matches the peer handoff.
2. **region = `us-east-1`** (SES-inbound-capable), resolved by the extant provider from
   `AWS_REGION`/profile. bucket co-located for simplicity (it may live anywhere, but same
   region is the simplest safe default).
3. the robot's send/read authorization attaches to whatever principal `AWS_PROFILE`
   already resolves to in the test account — **no new IAM user/access-key required for the
   test pass** (auth-status is `sts:GetCallerIdentity`, already available).
   ⚠️ this assumes that principal is a **role** (SSO / assumed-role). the extant writable
   grant is `DeclaredAwsIamRolePolicyAttachedInline` — role-only. there is NO
   `DeclaredAwsIamUserPolicyAttached*` resource in the repo (verified via the daos list). so
   if `AWS_PROFILE` resolves to an IAM **user**, this plan has no resource to attach to and
   the design must instead mint a dedicated role (or add a user-policy resource). see the
   fulcrum below — this is the deciding factor, not just a keys-vs-role taste call.
4. **least-privilege via inline policy** on that principal (`DeclaredAwsIamRolePolicyAttachedInline`,
   already writable) — we do NOT make the read-only `DeclaredAwsIamPolicy` dao writable.
5. `demo.ehmpathy.com` is a subdomain we control DNS for on cloudflare and whose apex mail
   we won't disturb.

### the open questions — triaged

each is tagged `[answered]` (settled now), `[research]` (blueprint-time external), or
`[wisher]` (only the wisher decides).

- **[answered] domain to verify**: the wish is authoritative — "for your tests, you can use
  `demo.ehmpathy.com`". the peer's `bot.ehmpath.com` was one instance; the test domain is
  `demo.ehmpathy.com`. settled by logic, no wisher ask needed.
- **[answered] receive-capable region**: verified `us-east-1` supports SES inbound + S3
  delivery (cited below). the vision reads region from the provider and fails loud if it is
  not receive-capable.
- **[answered, in part] principal SHAPE (part of the identity fulcrum)**: the repo's own
  `hazard.local-green-cicd-red` brief states local `test` creds map to the `ehmpathy-demo-sso`
  permission set — i.e. an **SSO assumed-role**, NOT an IAM user. so locally, case (a) holds:
  the ambient principal is a role. BUT an SSO-managed permission-set role is owned by SSO
  provisioning, so an ad-hoc inline policy on it is fragile — which argues for a **dedicated
  declared identity** (role) over the ambient one. the SHAPE is answered; the DESIGN choice
  below stays open.
- **[answered — wisher 2026-07-29] robot identity = dedicated role**: (a) confirmed. the

  SSO role. see decisions-locked.
- **[answered — wisher 2026-07-29] send-from scope = subdomain grain**: the
  `ses:SendRawEmail` grant is scoped to `*@demo.ehmpathy.com`, not a single address.
- **[answered — wisher 2026-07-29] verified addresses always declared**: the sandbox

- **[answered — wisher 2026-07-29] s3 in scope, lifecycle = an s3 config, three modes**: the

- **[answered — name check 2026-07-29] resource nouns verified vs aws CloudFormation**: S3 +

- **[research] SES v1 vs v2 identity api**: exact SDK command names + the DKIM token

## groundwork

### external research

- **SES inbound + S3, region support** — verified. classic three receive regions
  (`us-east-1`, `us-west-2`, `eu-west-1`) expanded to 7+ more in 2023 (incl. `us-east-2`).
  receipt-rule → S3 delivery is a documented, current path; the S3 bucket may be in any
  region while the SES endpoint + rule set must be in a receive-capable region. SES can KMS-
  encrypt before write.
- **SES sandbox** — new accounts send only to verified addresses at low quota until
  production access is granted (a one-time support step, not a declastruct resource).

### internal research (grounded against this repo)

- **no SES or S3 resources exist yet** — `Glob src/**/*{S3,Ses,s3,ses}*` returns only
  `Ec2InstanceSession` (incidental "Ses"). confirms the wish's gap list: all 5 new
  resources are net-new.
- **`DeclaredAwsIamPolicyDao` is read-only** — `set.findsert`/`upsert` throw
  (`src/access/daos/DeclaredAwsIamPolicyDao.ts:31-43`). confirms open-question 3; the
  vision routes around it via inline policy.
- **domain-object shape to conform to** —
  `src/domain.objects/DeclaredAwsCloudwatchLogGroup.ts` +
  `DeclaredAwsSsmParameterPlain.ts`: `interface` + `class extends DomainEntity`, static
  `primary`/`unique`/`metadata`/`readonly`/`nested`; `tags: DeclaredAwsTags | null` nested.
- **DAO shape to conform to** — `genDeclastructDao<typeof X, ContextAwsApi &
  ContextLogTrail>({ dobj, get:{one:{byPrimary,byUnique}}, set:{findsert,upsert,delete} })`.
- **provider registration is two-place** — the `daos` map in
  `getDeclastructAwsProvider.ts:116-173` AND the `DeclastructAwsProvider` type map; new
  resources must land in both.
- **reusable policy dobjs** — `DeclaredAwsIamPolicyDocument` + `DeclaredAwsIamPolicyStatement`
  (+ `DeclaredAwsIamRolePolicyAttachedInline`) already model policy bodies; the s3 bucket
  policy + the send grant reuse them, no new policy model.
- **acceptance contract** — `src/contract/sdks/.test/assets/resources.acceptance.ts`
  `getResources()` returns the declared array (order = apply order); the acceptance test
  asserts plan-inclusion + post-apply `KEEP`. `keyrack.source({ env:'test', owner:'ehmpath',
  mode:'lenient' })` sits at the top of every resources file.
- **dogfood provision** — `provision/aws.infra/account=demo/resources.*.ts` is where the
  demo account self-provisions; a `resources.mail.ts` peer belongs here.
- **identity conventions** — `exid` for user-chosen keys (vpc/ec2), `name`/`arn` for
  aws-native names (log group, ssm param). SES uses natural names (`domain`, bucket `name`,
  rule-set `name`) — no `exid` needed.

### terms / patterns to reuse

- name form: `DeclaredAws{Service}{Resource}`, acronym as one initial-capped word (`Ses`,
  `S3`).
- verbs: `getOne{X}` / `set{X}` (findsert/upsert), `DeclaredAws{X}Dao`, exported from
  `src/contract/sdks/index.ts`.
- tags: `{ managedBy: 'declastruct', purpose: '...' }` on every taggable resource.

## what is awkward

- **the cloudflare seam is the honest wart.** "provision the resources to send and read
  email" reads like one command, but DNS lives in a provider declastruct-aws does not own.
  the emitted-records mitigation is good, but a user's mental model ("i declared it, why is
  mail not here yet?") will bump into "you still have to paste DNS + await propagation." we
  should make the apply output *loud* about this hand-off so it is not a surprise.
- **verification is asynchronous and out-of-band.** the identity resource emits tokens at
  once, but `verificationStatus` only flips to verified after the human pastes DNS and aws
  polls it. so a fresh apply legitimately shows an `unresolved` identity that is not a
  failure — the `get` must model "unresolved" as a normal state, not drift and not an error.
  this fights the usual "declared = live" expectation.
- **one active receipt rule set per region** is a global singleton with a destructive
  set-active. if the account already uses SES receipt for another purpose, our set-active
  would hijack it. the "active" declared status is clean, but the singleton means two
  independent mail wishes in one region/account will contend — the fail-loud guard is
  essential, and it is a slightly odd constraint for a "just declare it" model.
- **classic vs v2 SES** is an uncomfortable pin: receipt rules force us onto the older v1
  api surface while the send path would prefer v2. we live in both — tolerable, not tidy.
- **sandbox** means the very first "send" test can only reach a verified address, so the
  "how easy is it" measurement has an asterisk until production access is requested.
