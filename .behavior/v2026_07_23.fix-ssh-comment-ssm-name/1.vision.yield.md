# 1.vision — SSM param name must encode the SSH comment

## the outcome world

### day-in-the-life

an operator declares an ssh-key authorization the obvious way — with the key exactly
as `ssh-keygen` produced it, comment and all:

```ts
DeclaredAwsEc2SshKeyAuthorized.as({
  instance: RefByUnique.as<typeof DeclaredAwsEc2Instance>({ exid: 'grove-1-box' }),
  publicKey: 'ssh-ed25519 AAAA... vlad@grove-laptop',
  comment: 'vlad@grove-laptop', // the ssh-keygen default: user@host
  user: 'ec2-user',
});
```

then `declastruct plan` and `declastruct apply` just work. the `@` in the comment is
a non-event — it never reaches an SSM param name, so AWS never rejects it.

### before / after contrast

| | before | after |
|---|--------|-------|
| param name | `/declastruct/ec2/ssh-keys/grove-1-box/vlad@grove-laptop` | `/declastruct/ec2/ssh-keys/grove-1-box/vlad-grove-laptop-<hash>` |
| AWS response | `ValidationException` (name has illegal `@`) | accepted — name is `[A-Za-z0-9._-]` only |
| operator burden | hand-edit key comment to a `@`-free token, per key | none — use the key as-is |
| where readable comment lives | in the name (and value) | a readable slug in the name + the full comment in the value |
| get / set derive name via | two separate inline interpolations | ONE shared transformer |

### the "aha" moment

the value clicks when an operator points declastruct at a **real, unedited** ssh key
and it applies clean. today, essentially every real key fails, because
`ssh-keygen`'s default comment is `user@host` and `@` is illegal in an SSM param name.
after this wish, the naive path is the correct path — a pit of success.

## user experience

### usecases & goals

- **authorize a real ssh key on an ec2 box** without pre-processing its comment
- **re-plan / re-apply** and converge to KEEP (get must derive the SAME name set wrote)
- **run distinct keys** on one instance — two different comments must map to two
  different names (no silent collision that would clobber one authorization)

### contract inputs & outputs

the public contract is **unchanged** — `DeclaredAwsEc2SshKeyAuthorized` keeps its
`{ instance, comment, publicKey, user }` shape. the fix is entirely internal: how the
SSM param **name** is derived from `{ instance.exid, comment }`. no field is added,
renamed, or removed.

### timeline

```
declare key (comment = user@host)
      │
      ▼
declastruct plan
      │  get: derive name = /declastruct/ec2/ssh-keys/<exid>/<sanislug(comment)>-<hash(comment)>
      │       GetParameter → null (absent) → CREATE
      ▼
declastruct apply
      │  set: derive name via the SAME transformer → PutParameter (accepted)
      │       value JSON still carries the readable comment
      ▼
declastruct plan (again)
      │  get: derive name via the SAME transformer → GetParameter → found → KEEP
      ▼
converged, zero drift
```

### the name-segment format

an already-SSM-safe comment keeps its **literal** segment (backward-compat); only a comment
with an illegal char takes the **slug + hash** combo:

```
commentIsSsmSafe = /^[A-Za-z0-9._-]+$/.test(comment)   // CHARSET-ONLY — no length gate

segment = commentIsSsmSafe
            ? comment                                          // literal — byte-identical to the pre-fix bare name
            : slug ? `${sanislug(comment)}-${hash(comment)}`   // unsafe → readable slug + collision-safe hash
                   : hash(comment)                             // empty-slug fallback (no lead `-`)

  sanislug(comment) = comment
                        .replace(/[^A-Za-z0-9._-]/g, '-')  // illegal chars → dash
                        .replace(/-+/g, '-')               // collapse dash runs (readability)
                        .slice(0, 40)                      // bound the DECORATIVE slug only
                        .replace(/^-+|-+$/g, '')           // trim lead/trail dash — runs AFTER
                                                           //   the slice, so a mid-run cut
                                                           //   cannot re-expose a dash at the end
                      → HUMAN-READABLE, lossy, decorative (e.g. vlad@grove-laptop → vlad-grove-laptop)
  hash(comment)     = asHashShake256(comment, { bytes: 8 }) from hash-fns → 16 hex chars
                      → the UNIQUENESS + determinism guarantee (collision-safe)

  the safety gate is CHARSET-ONLY — the pre-fix code used the comment verbatim with no length
  gate, so every ALREADY-WORKING (illegal-char-free) name — at ANY length — keeps its literal
  segment stable across the upgrade (no orphaned param, no forced re-create). the `40` bound
  is a DECORATIVE cap on the escaped-branch slug only; it must NOT gate the safe/unsafe
  decision, or a safe comment over 40 chars would re-orphan its pre-fix param. only the
  `@`-broken names (which never persisted, since AWS rejected them) change. the empty-slug
  fallback (segment = hash alone) avoids a lead `-` when an UNSAFE comment has no safe chars
  at all (e.g. `@@@`).
```

**hash source (decided)**: `hash-fns@3.0.0` (already a direct dep — `package.json:78`), via
`asHashShake256(comment, { bytes: 8 })` → a 16-char hex suffix. the slug carries
readability, so the hash only needs enough length to disambiguate — a truncated shake256
keeps the segment compact (`vlad-grove-laptop-a1b2c3d4e5f6a7b8`) and collision-safe for the
handful of keys per instance. no new dep, no hand-rolled crypto. hex output (`[0-9a-f]`) is
a strict subset of the SSM-legal charset.

the slug answers "who is this key for?" at a glance; the hash guarantees the name is
unique and stable. crucially this does **NOT** ship the naive replace as the collision
mechanism — the replace is decorative only, and the **hash** is what keeps distinct
comments distinct. so `a@b` → `a-b-<hash(a@b)>` and `a_b` → `a-b-<hash(a_b)>` differ,
because the hashes differ, even though their slugs match.

## mental model

- **to a friend**: "the ssh key's comment is `user@host`, and AWS won't let `@` into a
  parameter name. so the name becomes a readable slug of the comment (`vlad-grove-laptop`)
  plus a hash that guarantees it's unique — and the full comment still rides inside the value."
- **analogy**: a coat-check ticket with BOTH a name and a claim number. the name (slug)
  tells you whose coat it is at a glance; the claim number (hash) is what actually
  guarantees a unique, unambiguous match. the full label still hangs on the coat (the value).
- **their terms vs ours**: operators say "comment" / "key name". we say "SSM param name
  segment" / "name-derivation transformer". the wish keeps their word (`comment`) on the
  contract and hides our word behind it.

## evaluation

### how well it solves the goals

- **default key applies clean** — a `user@host` comment yields an all-safe name ✅
- **get/set/(del) agree** — one shared transformer is the single source of the name, so
  a re-plan finds exactly what apply wrote ✅
- **no collision** — the hash suffix is injective for practical purposes; two distinct
  comments derive two distinct names even when their readable slugs match, ruling out the
  naive `replace`-only approach ✅
- **readable comment preserved** — a readable slug is in the name AND the full comment is
  in the param value JSON ✅

### pros

- pit-of-success: naive path = correct path
- one transformer → get/set/del cannot drift apart (the core invariant)
- `hash-fns@3.0.0` is already a direct dep — `asHashSha256(message): Hash` returns
  64-char hex, inherently `[a-f0-9]` and thus SSM-safe; no new dep, no hand-rolled crypto
- **the name is human-readable AND collision-safe** — the slug tells you who the key is
  for; the hash guarantees uniqueness. best of both.

### cons / tradeoffs

- **the slug is lossy** — `vlad@host` and `vlad_host` slug to the same `vlad-host`, so the
  readable prefix alone is not a unique id. acceptable: it is decorative; the hash suffix
  disambiguates, so no correctness cost — just don't read the slug as authoritative.
- **the name is longer** — slug + `-` + hash vs a bare hash. bounded (slug is length-capped,
  hash fixed), so no SSM name-length risk; a small readability-for-length trade.
- **no full reverse** — the hash cannot be decoded back to the comment (the slug is a lossy
  hint). acceptable per the wish (the full comment lives in the value).

## edgecases & pit-of-success

- **`@` (the default)** — slug replaces it (`vlad-grove-laptop`), hash absorbs it; the headline case
- **other illegal chars** (`/`, spaces, unicode, `+`, `=`) — replaced in the slug, absorbed by the hash
- **empty comment** — slug is empty → segment is just `-<hash>` (still a valid, stable segment)
- **very long comment** — slug is length-capped + hash is fixed, so no SSM name-length blowup
- **two comments that differ only in an illegal char** (`a@b` vs `a_b`) — same slug
  (`a-b`), but the hash suffix keeps the two names distinct ✅ (the exact case the naive
  replace-only approach would collide)

## open questions & assumptions

### assumptions

1. **no del site is present today** — audit confirms `DeclaredAwsEc2SshKeyAuthorizedDao`
   sets `delete: null` and there is no `delEc2SshKeyAuthorized` operation. so the shared
   transformer must serve get + set today, and be the ONLY place a name is composed so a
   future del is forced through it. (assumption: the wish's "get/set/del agree" is
   satisfied by get+set agreement plus a single-source transformer; no del needs writing.)
2. **hashing is the chosen encode** — the wish marks sha256 hex as **preferred**; I take
   that path over a reversible encode.
3. **the readable comment in the value is sufficient** — confirmed: `setEc2SshKeyAuthorized`
   stores `comment` inside the JSON value (`setEc2SshKeyAuthorized.ts:82-88`), and
   `asEc2SshKeyAuthorized` reads it back from there — so hashing the name loses no info.
4. **the public contract must not change** — `DeclaredAwsEc2SshKeyAuthorized` keeps
   `comment` as its unique field; only name-derivation changes.

### open questions (triaged)

- **q1 [answered — logic + rules]: transformer name & scope.** it derives the FULL param
  name (`/declastruct/ec2/ssh-keys/${exid}/${hash(comment)}`), not just the hashed segment
  — so both call sites consume ONE identical string and cannot drift on the prefix either.
  named `asEc2SshKeyAuthorizedSsmParamName`, an `as*` transformer taking
  `{ instanceExid, comment }` per `rule.require.get-set-gen-verbs` +
  `rule.require.named-transformers`. resolved now; the wisher may rename at review, but the
  design does not block on it.
- **q2 [answered — rules + a live CI proof]: coverage for the `@` case.** the `@` failure
  is a pure string-derivation concern; `rule.require.test-coverage-by-grain` mandates a unit
  test for a pure transformer — so a transformer unit test with a `user@host` comment (proves
  the segment is SSM-safe) + a get/set-agreement test (proves the same name is derived both
  ways). the live acceptance seed (`declastruct-acceptance-seed`) stays un-churned. PLUS the
  headline "AWS accepts the derived name" is now proven LIVE IN CI by a standalone SSM round-
  trip test (`asEc2SshKeyAuthorizedSsmParameterName.integration.test.ts`): it does a real
  PutParameter→GetParameter on the `@`-derived name, needs only the ssm param grant (already
  at `resource: '*'` in `demoPermissionsPolicy`, both roles), so it runs UNCONDITIONALLY in
  CI — no active instance, no EC2 Instance Connect, no OIDC re-apply. this closes the earlier
  "the `@` case never runs live in CI" gap without any acceptance-seed churn or a wisher call.
- **q3 [answered — logic]: orphaned prior params / migration — OUT of scope.** the raw-`@`
  name NEVER persisted: every attempt threw `ValidationException` before the write
  (issue #73), so there is no raw-name param in AWS to migrate. the ONLY params that may
  exist under a non-hash name are ahbode's ephemeral `node_modules`-patch artifacts
  (`replace`-derived names like `vlad_pop-os`) on the grove-1 account — those are ahbode's
  operational artifacts, cleaned manually with `aws ssm delete-parameter` if desired, and
  are NOT this repo's code concern. this wish ships only the durable derivation change.
- **q4 [answered — wisher]: should `exid` also be encoded? NO.** the wisher confirmed: do
  NOT hash `exid`. the fix hashes only `comment` — every extant `exid` is already SSM-safe
  (`[a-z0-9-]`) and exid encoding is out of scope.

## groundwork — sanity check

the vision is NOT built on false assumptions:

- the bug is real and localized to two inline interpolations (read both files).
- the fix tool (`hash-fns`) is present, is already a dep, and returns SSM-safe output
  (read its readme).
- the readable comment survives because it lives in the value, not the name (read the
  set + cast).
- there is no del path to keep in sync today, but the single-transformer design forces a
  future del through the same derivation (read the DAO).

## what is awkward?

- **acceptance vs unit coverage for the `@` case.** the live acceptance fixture keeps the
  instance stopped for cost and seeds the key via a real SSM append — expensive to churn.
  the `@`-comment acceptance criterion is most cheaply proven at the **transformer unit**
  grain (pure, no AWS), plus a get/set-agreement test. this feels slightly off against the
  wish's phrasing ("`declastruct plan` no longer throws `ValidationException`"), which
  implies an end-to-end proof. the tradeoff: an inline name-derivation ValidationException
  is deterministic and fully captured by a pure transformer test; a full plan/apply round
  against AWS to prove a string-formatting fix is costly and slow for little added signal.
  I lean unit + agreement tests, and flag it here for the wisher (q2).
- **losing name readability.** operators who today `aws ssm get-parameters-by-path` and
  read the comment off the name lose that. minor — the value carries it — but it is a real
  behavioral shift worth naming.
- **the hash is one-way.** if a future need arises to enumerate "which comment is this
  param?", the answer requires a read of each value, not a parse of names. acceptable for
  the wish's scope, but it forecloses the reversible-encode path.
