# wish: fix — authorized-ssh-key get must reflect the box, not a stale SSM proxy

## .what (one sentence)

`getOneEc2SshKeyAuthorizedByUnique` decides an authorized key's live state from an SSM parameter
ALONE; because that parameter is keyed by the box's stable **exid** it outlives a
terminate-and-recreate, so after a rebuild the get reports a key that the fresh disk does not
carry — reconcile reads KEEP, `set` never re-lands the key, and the crew is locked out.

## .source (authoritative)

handed off inline in the dispatch. treat the acceptance below as the contract of record.

- **repo:** `ehmpathy/declastruct-aws`
- **files:**
  - `src/domain.operations/ec2SshKeyAuthorized/getOneEc2SshKeyAuthorizedByUnique.ts` (the defect)
  - `src/domain.operations/ec2SshKeyAuthorized/setEc2SshKeyAuthorized.ts` (context — the twin write)
- **version affected:** 1.9.0 (current)

## .why

`setEc2SshKeyAuthorized` correctly writes TWO layers:

1. the **real layer** — the box's `~/.ssh/authorized_keys` on its EBS disk, via an SSM shell
   command (the item that actually grants access)
2. the **track layer** — an SSM parameter `/declastruct/ec2/ssh-keys/{exid}/{comment}` (a record
   that the authorization happened)

but the get reads ONLY the track layer — it asks "does the PARAM exist", never "is the KEY on the
box". the track layer is a proxy, and the two diverge the moment the box is replaced: the
parameter is keyed by the STABLE exid (e.g. `grove-1`), not the ephemeral instance-id, so a
terminate-and-recreate leaves it untouched while the disk is wiped.

| step | real layer (box disk) | track layer (SSM param) | get decides |
|------|----------------------|-------------------------|-------------|
| first authorize | key present | param present | — |
| box rebuilt (same exid) | **empty** (fresh disk) | **still present** | KEEP (wrong) |

reconcile sees KEEP, skips `set`, and the fresh box never gets the key — `ssh` fails with
`Permission denied (publickey)` even though the wish and the parameter both claim the key is
authorized. the state is a lie the get cannot catch, because it never looks at the box.

## .acceptance (what proves it done — authoritative)

1. **an absent key on the box reads as absent** — given the SSM parameter exists BUT the box's
   `~/.ssh/authorized_keys` lacks the key line, the get returns `null` (not the declared key), so
   reconcile decides CREATE and `set` re-lands it.
2. **a present key still reads as present** — given the parameter exists AND the key line is on
   the box, the get returns the declared key (no spurious re-push).
3. **the rebuild path reconciles CREATE** — authorize a key, replace the instance under the SAME
   exid (fresh disk), then reconcile decides CREATE (re-push), NOT KEEP. this is the exact path
   that failed under 1.9.0.
4. additive + non-regressive — a box whose key is genuinely present generates the same decision
   as before; no change to `set`'s idempotent append.
5. **tests**:
   - unit — parameter present + key absent from the box → get returns null (RED before, GREEN after).
   - unit — parameter present + key present on the box → get returns the key.
   - journey (`ec2SshKeyAuthorized.journey.integration.test.ts`) — the rebuild case in acceptance #3.

## .the proposed shape (advisory — the mechanic owns the HOW)

### option a (preferred) — verify the key on the box, not just the param

have the get confirm the key line is actually present in the box's `authorized_keys` (via the same
SSM-command channel `set` already uses) and return null when absent, even if the parameter still
exists. the parameter then serves only as metadata (fingerprint, authorizedAt), never as the sole
source of truth for existence.

the handoff sketches: read the param; if absent → null; else cast the declared key, look up the
instance, and probe the box with a `grep -qF` over `authorized_keys` (key passed base64 so it
survives shell quotes) that prints PRESENT/ABSENT; treat any other result as null.

the trade favors verify: `set` is already idempotent (`grep -qF ... ||` appends), so a false null
costs at most one redundant re-push — benign. a false non-null (the current bug) costs a
locked-out crew.

### option b (complementary) — bind tracked state to instance identity

record the instance-id (or launch time) alongside the key in the parameter, and treat a parameter
whose instance-id no longer matches the live box as absent. cheaper (no SSM round-trip to the box)
but does NOT catch drift where the box is the same yet `authorized_keys` was edited out-of-band —
so option a is the fuller fix. ship both if you want the cheap check and the true one.

mirror the repo's extant probe/error patterns rather than a literal copy of the sketch. the
OUTCOME above (the get reflects the box, the rebuild path re-pushes) is the contract.

## .scope

- primary: the existence decision in `getOneEc2SshKeyAuthorizedByUnique.ts`, plus the tests in
  acceptance #5.
- release note: option a issues an SSM `SendCommand` from the READ path, so a caller's role needs
  `ssm:SendCommand` + `ssm:GetCommandInvocation` for reads too. most callers that can `set` a key
  already hold these; call it out for any read-only caller that previously needed only
  `ssm:GetParameter`.
