## the apply-order dependency (precise — corrects the vision's "benign" shorthand)

a legacy param (no recorded id) reads as stale → null → CREATE → the set re-pushes the key. the
re-push needs the box ACTIVE (the set runs an ssm command). so the migration is benign ONLY when the
box is active:

- in the declarative flow (`use.ssh.tunnel.ts`) the session resource (`status: active`) precedes the
  ssh-key resource, so the box is active before the set runs — benign as framed.
- a standalone apply of ONLY the ssh-key resource against a STOPPED box with a legacy param fails
  loud at the set (now with an actionable message). this is the SAME apply-order dependency any
  CREATE/rebuild re-push already has, and the fail-loud is APPLY-time — correct per
  `rule.forbid.plan-fail-on-apply-guided-prereq` (the get degrades to null at plan; the guided
  failure surfaces at apply). the old silent KEEP was the bug (it claimed a key it never verified);
  a loud, guided failure is the correct successor.

## ⚠️ RELEASE NOTE (for the PR / changelog)

**boxes with an extant ssh-key authorization must be ACTIVE for their first apply after this fix
ships.** every authorization written before this fix has a legacy (no-`instanceId`) param; on the
first post-upgrade `declastruct apply` it reads stale → CREATE → re-push, and the re-push needs the
box active (the set runs an ssm command). this is a one-time migration: after that first apply the
param carries the instance-id, and stop/start correctly reads KEEP forever after. for an idle
(stopped) box, start the session for that one apply — in the paved `use.ssh.tunnel` flow the session
resource precedes the ssh-key resource, so this is automatic.

## the read-path cost (precise — corrects "two cheap reads")

the get's stale-check calls `getEc2Instance`, which is NOT one api call: it chains
`DescribeInstances` → `getOneVpcSubnet` → N× `getOneVpcSecurityGroup`. this cost is paid on EVERY
plan-time `get.one.byUnique`, for every declared ssh-key resource, on every `declastruct plan` — i.e.
O(resources × (1 + 1 + N-sgs)) added describe calls per plan, not O(resources). it matches the extant
`getEc2InstanceSession` precedent, so it is not a new smell, but a lean id-only lookup
(`getOneEc2InstanceId`) is the right optimization once a SECOND consumer of "just the id" appears
(`rule.prefer.wet-over-dry` / `rule.prefer.most-common-denominator` — one consumer today).

  notes described — the get pays it once at plan; the set no longer pays it twice at apply.
- [x] **corrected the stale DAO doc** — `DeclaredAwsEc2SshKeyAuthorizedDao` said re-push happens "via
  EC2 Instance Connect"; the actual (and always-was) mechanism is SSM `SendCommand`. fixed in both
  the header and the inline comment.
- [x] **dropped non-repo-resolvable rule citations from code comments** — the ehmpathy/bhrain role

## the lean id-lookup (round i010) — the second consumer arrived, so the primitive landed

L3 `enroll-impl-arch-defects` pressed the read-path cost note above to its conclusion, and it was
right to: after the i009 fix removed the set's self-get, the get's `getEc2Instance` call was left as
the one over-broad lookup — and it is worse than "just cost". `getEc2Instance` HARD-THROWS
(`UnexpectedCodePathError`) when the subnet or any security group is not found; this wish INTRODUCED
that call into the get (before the fix the get never looked up the instance), so a transient VPC
hiccup at PLAN time would abort the ssh-key get — the exact failure
`rule.forbid.plan-fail-on-apply-guided-prereq` forbids (a plan-time get must degrade to null, not
a hard-throw). closed at the root:

- [x] **extracted a lean `getOneEc2InstanceId` primitive** —
  `src/domain.operations/ec2Instance/getOneEc2InstanceId.ts` runs the `DescribeInstances`, handles
  the not-found/collision cases, and returns the id (or null); NO subnet/SG resolution, so it
  degrades to null instead of a hard-throw on a VPC sub-lookup.
- [x] **pointed BOTH ec2SshKeyAuthorized call sites at it** — the get's stale-check (degrades to
  null → CREATE, never aborts the plan) AND the set (it only ever read `instance.id`). the set is
  the genuine SECOND consumer the earlier note said to wait for — it arrived, so the primitive is
  justified NOW, not speculatively (`rule.prefer.most-common-denominator`). the cost note's
  "one consumer today" precondition is superseded.
- [x] **left `getEc2Instance` untouched** — it has ~15 consumers; a refactor of it in a fix release
  is the larger-risk move. the modest describe-command duplication is the right trade for a bounded
  fix; the full compose-on-top decomposition is the cleaner end state but a wider change than this
  wish warrants. green: types, lint, unit 34/34.
