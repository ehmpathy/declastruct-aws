### why the re-run fared WORSE (0/43) — the perf defect is the cause

the acceptance suite runtime (~65 min) EXCEEDS the AWS SSO session-token window, so the token
lapses partway through the run and every subsequent `declastruct plan` subprocess loses its
credentials. this is not a feature issue — it is the acceptance-suite perf defect (below) that
actively broke the run's own auth. a faster suite completes inside the token window and never hits this.

## follow-up note (out of scope for this patch `fix:`) — acceptance-suite perf defect

**severity: blocker for CI/CD reliability; NOT a metadataOptions concern.**

the `declastruct.acceptance.test.ts` suite takes ~65 min, long enough that the SSO session token
expires mid-run (see above). profile from `2026-07-28T02-58-31Z` (assertions total ~4.5 min,
so ~60 min is redundant setup):

- `apply same plan twice succeeds` (idempotency, line 739) — **224 s** for one full 37-resource re-apply
- the full-stack plan is recomputed as **3 separate cold `npx declastruct` processes** — the
  `when('generating a plan')` (l.316), `when('applying a plan')` (l.628), and
  `when('re-planning after apply')` (l.763) blocks; each pays a fresh Node+ts boot AND re-reads
  all 37 resources' live state
- the full stack is applied **twice** (l.634 + l.746)

**the fix (a separate change):** share ONE plan/apply across the assertion blocks; drop the redundant
cold `npx` re-plans in favor of one in-process provider; scope the idempotency re-apply to a small
subset instead of the whole stack. this should cut ~65 min → <10 min, which also closes the
SSO-expiry-mid-run failure mode. it touches EVERY resource's test path and predates this feature,
so it belongs in its own PR, not this patch metadataOptions `fix:`.

## live-AWS steps — need foreman go-ahead (hard-to-reverse infra)

the remaining two suites (integration + acceptance) run against the live demo AWS account. the
acceptance path in particular REQUIRES a **prune-then-recreate** of the shared, immutable EC2
fixtures, because the feature changes their metadata posture:

- the extant acceptance/demo launch templates (`declastruct-acceptance-template`,
  `declastruct-acceptance-nat-template`, `declastruct-demo-box-template`,
  `declastruct-demo-nat-template`) predate this feature → read back imdsv1-allowed ≠ the secure
  default → plan a change → a launch template is IMMUTABLE → apply fails loud → they must be pruned
  (`aws.prune.ec2.sh`) and recreated secure. this is the exact prune-then-recreate the vision names
  (`rule.forbid.test-blocking-orphans`).
- pruning terminates live EC2 instances + deletes launch templates in the shared demo account — a
  destructive, hard-to-reverse action on shared infrastructure. holding for foreman go-ahead before
  the live prune + apply.
