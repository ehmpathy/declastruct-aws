# 1.vision — feat(ec2): IMDSv2 MetadataOptions on launch template

vision of the world when the wish `.behavior/v2026_07_26.feat-ec2-imdsv2-metadata-options/0.wish.md`
is fulfilled.

---

## the outcome world

### day-in-the-life

an ehmpathy/ahbode engineer declares an EC2 box the way they always have — a
`DeclaredAwsEc2LaunchTemplate` with an instance type, an AMI, a root volume, an IAM
instance profile. they write **no metadata field**. they `declastruct apply`.

the box comes up **IMDSv2-only**: `httpTokens=required`, `httpPutResponseHopLimit=1`,
`httpEndpoint=enabled`. the instance-role credentials are no longer reachable by a bare
`GET http://169.254.169.254/...` from an SSRF or a hopped container — a caller now needs
the PUT-token handshake that IMDSv1 never demanded.

the engineer who *does* run docker on the box overrides just the hop limit off the exported
secure default — `metadataOptions: { ...ec2InstanceMetadataOptionsSecure,
httpPutResponseHopLimit: 2 }` — and containers can still reach the metadata endpoint through
the extra network hop. (all three sub-fields are required on the object, so the spread carries
the two it does not change; the field is not `?`-optional by design, per
`rule.forbid.undefined-attributes`.) the engineer who genuinely needs the old behavior (rare,
legacy) opts out explicitly with `metadataOptions: { ...ec2InstanceMetadataOptionsSecure,
httpTokens: 'optional' }`. the opt-out is a visible, reviewable line in the declaration, not a
silent default.

### before / after

| | before | after |
|---|---|---|
| declared box, no metadata field | IMDSv1-allowed (`HttpTokens: optional`) | IMDSv2-only (`required`, hop 1, enabled) |
| credential reach via SSRF/container | open — one GET to 169.254.169.254 | closed — needs PUT-token handshake |
| launch under `MetadataHttpTokens == required` SCP | **RunInstances denied** — option never set | allowed — option is set |
| docker on the box | (n/a — no control) | one field: `httpPutResponseHopLimit: 2` |
| plan/apply on an unchanged box | KEEP | KEEP (default converges, no spurious diff) |

### the aha moment

the value clicks when an engineer runs `declastruct plan` on a box they declared with
**no** metadata field and sees the box is already IMDSv2-only — the secure posture was the
*default*, not a thing they had to remember. and when the ahbode camp SCP (`deny
RunInstances unless MetadataHttpTokens == required`) stops rejecting declastruct launches,
because declastruct now speaks the option the guardrail demands.

## user experience

### usecases & goals

- **enforce IMDSv2 on every managed box** without touching every declaration (secure default).
- **launch under a security guardrail SCP** that requires `MetadataHttpTokens == required`.
- **opt a box into container-friendly hop limit** (`2`) when it runs docker.
- **opt a box out** back to IMDSv1 when a legacy workload genuinely needs it — explicitly.
- **detect drift**: a box whose metadata posture was changed out-of-band plans a change.

### contract inputs & outputs

the new input is an optional `metadataOptions` on `DeclaredAwsEc2LaunchTemplate`, a small
nested value object carrying the three IMDSv2 controls:

```ts
DeclaredAwsEc2LaunchTemplate.as({
  exid: 'grove-box',
  instanceType: 't3.micro',
  imageId: 'ami-...',
  hibernation: false,
  rootVolumeSize: 16,
  rootVolumeEncrypted: true,
  iamInstanceProfile: RefByUnique.as({ name: 'grove-role' }),
  userData: null,
  tags: null,
  // NEW — omit for the secure default:
  // metadataOptions: { httpTokens: 'required', httpPutResponseHopLimit: 1, httpEndpoint: 'enabled' },
});
```

three leverage shapes:

```ts
// 1. secure default — omit the field entirely (the common case)
metadataOptions: null            // → box is required / 1 / enabled

// 2. docker/container box — bump the hop limit
metadataOptions: { httpTokens: 'required', httpPutResponseHopLimit: 2, httpEndpoint: 'enabled' }

// 3. explicit opt-out — legacy IMDSv1 workload
metadataOptions: { httpTokens: 'optional', httpPutResponseHopLimit: 1, httpEndpoint: 'enabled' }
```

the output: the created launch template carries `MetadataOptions`, and read-back
(`getEc2LaunchTemplate` → `castIntoDeclaredAwsEc2LaunchTemplate`) reflects it, so plan/apply
converge to **KEEP** on an already-correct box.

### timeline

```
given  an engineer declares a launch template with no metadataOptions
when   they `declastruct apply`
then   AWS creates the template with MetadataOptions = required / 1 / enabled
 and   the instance launched from it (Version: $Latest) inherits IMDSv2-only

given  the same declaration, re-applied
when   `declastruct plan`
then   read-back equals declared → KEEP (no spurious diff)

given  a box that predates this feature (IMDSv1-allowed)
when   `declastruct plan` with the (now secure-default) declaration
then   read-back (optional) ≠ secure default → a change is planned
 and   because a launch template is IMMUTABLE, apply does NOT heal in place —
       set.upsert fails loud; the operator prunes the old template + instance and
       re-applies to create them secure (prune-then-recreate,
       rule.forbid.test-blocking-orphans)
```

## mental model

### how a user describes it to a friend

> "declastruct now locks the metadata service to v2 by default — so a leaked SSRF can't
> just curl the instance role's creds anymore. i didn't have to change anything; my boxes
> came up locked. if i run docker i bump one number for the extra hop."

### analogies

- **a deadbolt that ships locked.** the old door (IMDSv1) opened with a push; the new door
  (IMDSv2) needs you to turn the key first (the PUT-token handshake). and it ships locked —
  you have to *choose* to leave it unlocked.
- **the pit of success**: the easy path (declare no field) is the safe path (IMDSv2-only).

### their terms vs our terms

| they say | we say |
|---|---|
| "lock the metadata service" / "kill IMDSv1" | `httpTokens: 'required'` |
| "let docker reach metadata" | `httpPutResponseHopLimit: 2` |
| "turn metadata off entirely" | `httpEndpoint: 'disabled'` |
| "the secure default" | absent `metadataOptions` → required / 1 / enabled |

we adopt AWS's own field names (`httpTokens`, `httpPutResponseHopLimit`, `httpEndpoint`)
so the declaration mirrors the CFN `MetadataOptions` shape — ubiqlang fidelity, no synonyms.

## evaluation

### how well it solves the goals

- **enforce IMDSv2 everywhere**: yes — secure-by-default means every *new* declastruct box
  is IMDSv2-only with zero caller effort; the acceptance box proves it.
- **launch under the SCP**: yes — `MetadataOptions.HttpTokens: required` is now sent on
  create, so `MetadataHttpTokens == required`-gated `RunInstances` is satisfied.
- **container hop / opt-out**: yes — one explicit field each.
- **drift detection & KEEP**: yes, *given the convergence design is right* (see awkward §).

### pros

- highest-leverage security default in the package — one field, every box hardened.
- additive: extant declarations with no `metadataOptions` keep working (now safer).
- the launch-template path alone hardens the **instance**, because `RunInstances` launches
  from the template at `Version: $Latest` and **inherits** its `MetadataOptions`
  (`setEc2Instance.ts:229-243`). so we get the security win without touching the instance path.

### cons / tradeoffs

- a box that *relied* on IMDSv1 will now plan a change on next apply — intended (that is the
  point), but a caller who never opted out could be surprised by a diff. mitigated: the diff
  is visible in plan, and the fix (`httpTokens: 'optional'`) is one line.
- `httpEndpoint: 'disabled'` is expressible and would break instance-role usage entirely — a
  foot-gun the field surface allows (AWS allows it too). we mirror AWS rather than forbid.

### edgecases & pit-of-success

| edgecase | how the contract keeps the user safe |
|---|---|
| caller declares no field | secure default applied — IMDSv2-only, not IMDSv1 |
| caller re-applies unchanged | KEEP (default must converge — the fulcrum below) |
| legacy IMDSv1 box, no opt-out | plan shows a change; template is immutable so apply fails loud → prune-then-recreate to make it secure |
| docker box needs hop 2 | one explicit field; default stays 1 for non-docker |
| out-of-band change to metadata posture | read-back ≠ declared → drift surfaced (given cast reads live truth, `rule.require.immutable-source-of-truth`) |

## open questions & assumptions

### assumptions

1. **the launch-template path is sufficient for the security outcome.** grounded: instances
   launch from the template at `$Latest` and inherit `MetadataOptions`
   (`setEc2Instance.ts:232-235`). so landing the launch-template path here, and deferring the
   instance-path `RunInstancesCommand` override to a scoped follow-up, still delivers the
   secure box. **best-guess: land launch template only in this behavior; note instance path
   as follow-up** (the wish explicitly permits this). — *flagged for the wisher.*
2. **the three defaults are the contract** (`required` / `1` / `enabled`) — taken verbatim
   from the wish/issue #77. not a design choice; a given.
3. secure-by-default means the default is applied at *create/declare* time, and read-back
   reflects the actual AWS value (honest drift), per `rule.require.immutable-source-of-truth`.
4. **we model three of AWS's five configurable metadata sub-fields.** AWS's
   `LaunchTemplateInstanceMetadataOptions` (models_1.d.ts:7668-7736) carries five settable
   sub-fields plus a read-only `State`; we model the three the wish names (`httpTokens`,
   `httpPutResponseHopLimit`, `httpEndpoint`) and deliberately omit `HttpProtocolIpv6` and
   `InstanceMetadataTags` (both default `disabled` at AWS). the cast reads back only the three
   modeled fields, so the two omitted (defaulted-`disabled`) fields never enter the compare —
   KEEP stays intact. a future need for either is an additive follow-up, same shape as this
   wish. this is a wisher-sanctioned scope boundary (issue #77 lists exactly three), named
   here so the omission reads as deliberate, not an oversight.

### the key fulcrum — how does an absent declaration converge to KEEP?

this is the one real design decision the vision exposes (the HOW is the mechanic's, but the
vision must name it). when a caller declares **no** `metadataOptions`:

- the box is created with `required / 1 / enabled` (secure default), but
- read-back from AWS returns `required / 1 / enabled` (the real value), while
- the declared field is `null`.

so a naive compare (`null` vs `{required,1,enabled}`) would plan a **spurious change** —
in breach of acceptance #4 (KEEP). two candidate resolutions:

- **(A) collapse on both ends**: `null` means "secure default"; the set path expands
  `null → {required,1,enabled}` on the SDK call, and the cast path collapses a read-back that
  *equals* the secure default back to `null`. then `null` (declared) == `null` (read) → KEEP,
  while a legacy `optional` box reads as `{optional,...}` ≠ `null` → a change is planned and
  healed. **← best-guess: cleanest; honest drift AND KEEP.**
- **(B) materialize the default in the domain object** so an absent field always becomes
  `{required,1,enabled}` at declaration; then declared == read → KEEP. simpler compare, but
  every declaration now carries an explicit object even when the caller wrote no field.

**best-guess (A)**; both satisfy the acceptance. flagged for the mechanic/wisher — a clean
rework either way (it is internal cast/set logic, no public-contract change).

### open questions — triaged

- **[wisher]** confirm **launch-template-only** scope for this behavior, with the instance-path
  `RunInstancesCommand` override as a scoped follow-up (assumption 1). only the wisher can set
  scope; the wish permits either, so this is a scope confirmation, not a technical unknown.
- **[answered]** the KEEP-convergence approach (fulcrum A vs B). resolved now by logic:
  best-guess **A** (collapse `null`↔secure-default on set/cast) — it gives honest drift AND
  KEEP with no public-contract change. this is internal HOW the mechanic owns; both A and B
  satisfy the acceptance, so no wisher input is needed.
- **[answered]** does an instance inherit the template's `MetadataOptions`? resolved by code +
  docs: `RunInstances` launches from the template at `$Latest` and sets no override
  (`setEc2Instance.ts:229-234`); AWS launch-template semantics apply the template's config to
  the instance unless the request overrides it. empirically re-proven at the acceptance stone
  (the acceptance box reads back IMDSv2-only).
- **[answered]** hop-limit default of `1` (not `2`). resolved by the wish: `1` is the stated
  secure default, `2` is the explicit container opt-in. the fleet's containerization mix is the
  wisher's context, already weighed in issue #77.
- **[answered]** which of AWS's sub-fields to model. resolved by the wish (issue #77 names
  exactly three) + code (assumption 4): model three, omit `HttpProtocolIpv6` /
  `InstanceMetadataTags` (both default `disabled`, KEEP-safe), additively extensible.

### research needed

- **[research]** empirical confirmation of instance inheritance under a real apply happens at
  the **acceptance stone** (the acceptance box, launched from the template, reads back
  IMDSv2-only). this is scheduled verification, not an open unknown — the behavior is
  documented; the acceptance test proves it in-repo.
- otherwise none remaining beyond what is verified in the groundwork below.

## what is awkward?

1. **the KEEP-convergence fulcrum (above)** is the sharpest awkwardness: "secure default when
   absent" + "read-back equals declared → KEEP" are in mild tension, because the default the
   box gets is not textually the `null` the caller wrote. resolvable (fulcrum A/B) but it is
   the one spot where the design has to be deliberate rather than mechanical.
2. **a value object for three scalars** feels slightly heavy — but it mirrors the extant
   `DeclaredAwsEc2InstanceNetwork*` nested-literal convention and keeps the field surface
   grouped, so it is the right kind of heavy (symmetry over a flat triple of top-level fields).
3. **`httpEndpoint: 'disabled'` is a foot-gun the surface allows** — it would blind the
   instance role entirely. we mirror AWS rather than constrain, so the pit-of-success relies
   on the *default* (enabled) rather than on forbidding the unsafe value.
4. **the secure default silently changes posture on legacy boxes** — a box that quietly ran
   IMDSv1 will plan a change with no opt-out. this is intended (the security win), but it is a
   behavior-change-on-upgrade, not a pure addition, for boxes that never declared the field.
   the wish's acceptance #5 frames this as expected ("now with the secure default applied").
