# wish: feat(ec2) — support IMDSv2 MetadataOptions on launch template + instance

## .what (one sentence)

add optional IMDSv2 `metadataOptions` to `DeclaredAwsEc2LaunchTemplate` (and ideally
`DeclaredAwsEc2Instance`), pass it through to the AWS SDK on create, and read it back so
plan/apply converge to KEEP — secure-by-default (IMDSv2-required) when the field is absent.

## .source (authoritative)

the full write-up — motivation, the three absent-field sites, and the proposed shape —
lives in the GitHub issue. treat that as the spec of record:

- `ehmpathy/declastruct-aws` issue **#77** ("feat(ec2): support IMDSv2 MetadataOptions on
  launch template + instance")

## .why

today declastruct cannot enforce IMDSv2 on a managed EC2 box:

- `DeclaredAwsEc2LaunchTemplate` has no `metadataOptions` field.
- `setEc2LaunchTemplate`'s `CreateLaunchTemplateCommand` sends no `MetadataOptions`.
- `setEc2Instance`'s `RunInstancesCommand` sends no `MetadataOptions`.

so every declastruct-launched instance defaults to IMDSv1-allowed (`HttpTokens: optional`),
which makes the instance-role credentials reachable via any SSRF or container hop. for the
ahbode camp grove boxes, that instance role is the cross-account reach identity into
prep/prod — a direct credential-theft path. further: an org SCP that denies
`ec2:RunInstances` unless `ec2:MetadataHttpTokens == required` will block every declastruct
RunInstances call, because the option is never set — so the absent field also breaks box
launch under a common security guardrail.

## .acceptance (what proves it done — authoritative)

1. an optional `metadataOptions` on the launch-template domain object carries the IMDSv2
   controls: `httpTokens` (required|optional), `httpPutResponseHopLimit` (number),
   `httpEndpoint` (enabled|disabled).
2. **secure-by-default**: when `metadataOptions` is absent, the created box is IMDSv2-only —
   `httpTokens=required`, `httpPutResponseHopLimit=1`, `httpEndpoint=enabled` — so every
   declastruct box is IMDSv2-only unless a caller opts out. (hop limit 2 is the documented
   choice for docker/containers; a caller sets it explicitly.)
3. the option flows to the SDK as `MetadataOptions` on `CreateLaunchTemplateCommand` (and
   ideally `RunInstancesCommand`).
4. read-back convergence: `castIntoDeclaredAwsEc2LaunchTemplate` + `getEc2LaunchTemplate`
   read the field back, so a plan/apply on an already-correct box converges to **KEEP** (no
   spurious diff), and a box that lacks it plans a change.
5. additive + non-regressing: extant launch templates / instances with no `metadataOptions`
   still create and converge (now with the secure default applied) — no prior path breaks.
6. tests cover: the secure default (absent field → required/1/enabled), an explicit opt-out
   (`httpTokens=optional`), and the read-back KEEP convergence.

## .the proposed shape (advisory — the mechanic owns the HOW)

issue #77 sketches the exact field names + defaults above. those defaults ARE part of the
outcome (secure-by-default is the point), so treat them as the contract. the field's
placement, the domain-object nested-hydration wiring, and whether the instance path lands in
this behavior or a follow-up are the mechanic's call — mirror the repo's extant declastruct
field-flow pattern (how other fields thread domain-object → set → cast → get) rather than a
literal copy of the sketch. if the instance-path (`RunInstancesCommand`) is materially bigger
than the launch-template path, land the launch template here and note the instance path as a
scoped follow-up.

## .scope

- primary: `DeclaredAwsEc2LaunchTemplate` domain object + `setEc2LaunchTemplate`
  (`CreateLaunchTemplateCommand`) + `castIntoDeclaredAwsEc2LaunchTemplate` +
  `getEc2LaunchTemplate` (read-back).
- ideally also: `DeclaredAwsEc2Instance` + `setEc2Instance` (`RunInstancesCommand`) — or a
  scoped follow-up if it materially grows the change.
- add the tests in acceptance #6.
