# 1.vision — fix: launch template must target the AMI's real root device

## the outcome world

### day-in-the-life

a platform engineer at ahbode declares a grove-box launch template. they cut the box's
AMI over from amazon-linux-2023 to ubuntu-24.04-LTS. the box declares
`hibernation: true` + `rootVolumeEncrypted: true`. they bump `declastruct-aws` and run
their rebuild.

- **before (1.9.0):** the template builds cleanly, so it *looks* fine. then the box's
  `RunInstances` dies with
  `UnsupportedHibernationConfiguration: For hibernation, the root device volume must be
  encrypted.` the engineer has no idea why — the template says `rootVolumeEncrypted: true`.
  the real root (`/dev/sda1`) launched UNencrypted from the AMI snapshot, because the
  encrypt override landed on a phantom `/dev/xvda` the ubuntu image never had. worse, the
  `rootVolumeSize: 32` was silently dropped too — the box came up at ubuntu's default size.
  declastruct-aws is effectively amazon-linux-only.

- **after (this fix):** the template's block-device override targets `/dev/sda1` — the AMI's
  ACTUAL root device name, read from `DescribeImages(...).Images[0].RootDeviceName`. the
  encrypt + size + gp3 override lands on the real root. `RunInstances` accepts the
  hibernation config. the box comes up encrypted at 32GB. the engineer never notices the
  device-name detail — it just works, on ANY AMI family.

### before/after contrast

| dimension | before (1.9.0) | after |
|-----------|----------------|-------|
| root device name | hardcoded `/dev/xvda` | AMI-derived from `RootDeviceName` |
| ubuntu AMI encrypt | silently dropped (phantom device) | lands on real root |
| ubuntu AMI size override | silently dropped | lands on real root |
| absent `RootDeviceName` | n/a (never looked up) | fail-loud named throw |
| amazon-linux AMI | works | works, identical |

### the "aha" moment

> "the override was there all along — it was just aimed at a device name that only
> amazon-linux images happen to use. AWS matches the override to a block device BY NAME, so
> the name has to be the AMI's real root, and that's AMI-specific."

the value clicks the moment someone sees the emitted `CreateLaunchTemplateCommand` input
carry `/dev/sda1` for a ubuntu AMI instead of `/dev/xvda`.

## user experience

### usecases / goals

- **declare a launch template for a non-amazon-linux AMI** (ubuntu, debian, RHEL, …) and
  have the root-volume override actually apply — the primary goal.
- **declare hibernation + encrypted root on any AMI** and have `RunInstances` accept it.
- **keep amazon-linux templates working exactly as before** — zero-regression is a goal in
  its own right (this is a live, depended-on path).

### contract inputs & outputs

the caller-facing contract is **unchanged** — `setEc2LaunchTemplate({ findsert | upsert })`
takes the same `DeclaredAwsEc2LaunchTemplate` it always did (`exid`, `instanceType`,
`imageId`, `hibernation`, `rootVolumeSize`, `rootVolumeEncrypted`, `iamInstanceProfile`,
`userData`, `tags`). the fix is entirely INTERNAL to how the block-device map is built:

```ts
// the caller writes exactly what they wrote before — no new required field
const template = DeclaredAwsEc2LaunchTemplate.as({
  exid: 'grove-box',
  instanceType: 't3.medium',
  imageId: 'ami-0ubuntu2404...',   // a ubuntu AMI whose real root is /dev/sda1
  hibernation: true,
  rootVolumeSize: 32,
  rootVolumeEncrypted: true,
  iamInstanceProfile: null,
  userData: null,
  tags: { managedBy: 'declastruct' },
});
await setEc2LaunchTemplate({ findsert: template }, context);
```

what changes is what AWS receives:

```jsonc
// before — override aimed at a device ubuntu lacks
"BlockDeviceMappings": [{ "DeviceName": "/dev/xvda", "Ebs": { "Encrypted": true, "VolumeSize": 32, ... } }]

// after — override aimed at the AMI's real root
"BlockDeviceMappings": [{ "DeviceName": "/dev/sda1", "Ebs": { "Encrypted": true, "VolumeSize": 32, ... } }]
```

### timeline (internal, per `setEc2LaunchTemplate` call that creates)

1. read `template` from `findsert ?? upsert` (unchanged)
2. `getEc2LaunchTemplate` by unique — findsert-return or immutable-upsert-throw (unchanged)
3. **NEW:** `DescribeImages({ ImageIds: [template.imageId] })` → read
   `Images?.[0]?.RootDeviceName`
4. **NEW:** if `RootDeviceName` is absent → throw a named error (`UnexpectedCodePathError`)
   with `imageId` in context — never a silent fallback to a guess
5. `CreateLaunchTemplateCommand` with `BlockDeviceMappings[0].DeviceName = <RootDeviceName>`,
   the same Ebs override as before (encrypt / size / gp3 / DeleteOnTermination)
6. read-back via `getEc2LaunchTemplate` by primary, return domain object (unchanged)

## mental model

### how a user describes it to a friend

> "declastruct's launch template used to assume every AMI names its root disk `/dev/xvda`
> like amazon-linux does. ubuntu names it `/dev/sda1`, so the encryption and size settings
> quietly missed. now it asks AWS what the AMI's real root disk is called and points the
> settings at that."

### analogies / metaphors

- **the mislabeled locker.** you put your gear (encryption, size) in locker `/dev/xvda`,
  but this gym numbers its lockers `/dev/sda1`. your gear sits in a locker that isn't
  yours. the fix reads the gym's real locker number first.
- **addressing a letter.** the override is a letter to the root volume; the device name is
  the address. a hardcoded address only reaches houses that happen to use it.

### terms: theirs vs ours

| user says | we say |
|-----------|--------|
| "root disk", "boot disk" | root device / `RootDeviceName` |
| "the encryption didn't take" | override landed on a phantom device (name mismatch) |
| "it worked on amazon linux, broke on ubuntu" | device-name divergence across AMI families |
| "AWS rejected my box" | `RunInstances` `UnsupportedHibernationConfiguration` |

## evaluation

### how well it solves the goals

- **solves the primary goal fully** — the override now lands on the real root for any AMI,
  proven by the ahbode live patch (built with `/dev/sda1`, box launched encrypted 32GB,
  hibernation accepted).
- **fail-loud on the one unknowable** — if AWS can't tell us the root name, we throw with
  context rather than guess, keeping the pit-of-success.
- **zero-regression** — amazon-linux AMIs still derive `/dev/xvda` (their real root), so
  extant callers are byte-identical.

### pros

- caller contract unchanged — no migration, no breaking change; ships as a minor.
- authoritative source — `RootDeviceName` comes from AWS itself, not a lookup table we'd
  have to maintain per AMI family.
- mirrors extant repo patterns — same `@aws-sdk/client-ec2` client, same
  `UnexpectedCodePathError.throw(msg, { context })` fail-loud shape already in this file.

### cons / costs

- **one extra AWS read per create** — a `DescribeImages` round-trip added to the create
  path. negligible latency; only on create (not on findsert-return).
- **a new IAM action** — callers need `ec2:DescribeImages`. covered by `ec2:*` /
  `AmazonEC2ReadOnlyAccess` / `ReadOnlyAccess`, so this repo's own demo + OIDC roles already
  hold it (see open-question #2); only EXTERNAL hand-scoped callers must add it. must be called
  out in release notes (the wish flags this).

### edge cases & pit-of-success

| edge case | how the contract keeps the user safe |
|-----------|--------------------------------------|
| ubuntu / non-`/dev/xvda` AMI | override lands on real root — the whole point |
| `DescribeImages` returns no `RootDeviceName` (bad/absent AMI id) | named throw with `imageId` — no silent phantom-device guess |
| amazon-linux AMI | derives `/dev/xvda` (its real root) — identical to before |
| findsert on extant template | returns early BEFORE the `DescribeImages` call — no wasted read, no new failure surface on the idempotent path |
| upsert on extant template | throws immutable-error BEFORE `DescribeImages` — unchanged |

## open questions & assumptions

### assumptions made

1. **`Images[0]` is the right image.** `DescribeImages({ ImageIds: [imageId] })` returns at
   most one image for a specific id, so `Images?.[0]` is safe. (a filter-based describe
   could return many; an id-based one cannot.)
2. **`RootDeviceName` is always present for a valid, describable AMI.** absence signals a
   bad/inaccessible `imageId` → the fail-loud path. this matches the wish's acceptance #2.
3. **the fix belongs on the create path only.** the findsert-return and immutable-upsert
   paths exit before block-device construction, so they need no `DescribeImages` read. this
   keeps the idempotent path cheap (aligns with the DAO idempotency briefs).
4. **`UnexpectedCodePathError` is the right named error.** it's the error class already used
   for the other fail-loud throws in this exact file — symmetry over novelty. (build-stone
   nuance: an absent `RootDeviceName` is arguably a CALLER's bad `imageId`, which the repo
   models as `ConstraintError`/exit-2 — the build stone should consciously pick between the
   two; the vision defaults to the wish's `UnexpectedCodePathError` for file-symmetry.)
5. **a `DescribeImages` CALL fault propagates loudly, distinct from the absent-name throw.**
   the fix adds two failure modes, not one: (a) the call RETURNS but `RootDeviceName` is
   absent → the named acceptance-#2 throw; (b) the call ITSELF faults — e.g. `AccessDenied`
   when a hand-scoped caller lacks `ec2:DescribeImages`, or a throttle/network fault → this
   must PROPAGATE (failfast, wrapped with `imageId` context), never be `try/catch`-swallowed
   into a fallback or mislabeled as an absent-name error (`rule.forbid.failhide`). the build
   stone must keep these two paths distinct.

### open questions (triaged)

1. **[answered] `DescribeImages` returns `RootDeviceName`** — verified against the INSTALLED
   SDK types, not just docs: `node_modules/.pnpm/@aws-sdk+client-ec2@3.943.0/.../dist-types/
   models/models_7.d.ts:2017` declares `RootDeviceName?: string | undefined` on the `Image`
   model (the `DescribeImages` response element). the field is typed optional → the fail-loud
   path (acceptance #2) is real, not hypothetical. ✓ (also matches the wish's live proof.)

2. **[answered — via code, CORRECTED in execution] the demo/OIDC roles need NO IAM change —
   `ec2:DescribeImages` is already covered.** an earlier draft of this question concluded a
   grant MUST be added, from the fact that `demoPermissionsPolicy`'s INLINE statements grant no
   `ec2:Describe*`. trust-but-verify corrected it: `demoPermissionsPolicy`
   (`provision/aws.auth/resources.common.ts:39`) attaches the AWS-managed policy
   `arn:aws:iam::aws:policy/ReadOnlyAccess`, which grants ALL `ec2:Describe*` — including
   `ec2:DescribeImages` AND the `ec2:DescribeLaunchTemplates` that `getEc2LaunchTemplate`
   already depends on (this is precisely why the launch-template acceptance passes today with
   NO inline `ec2:DescribeLaunchTemplates` grant). since the SAME `demoPermissionsPolicy` feeds
   both the SSO permission set and the OIDC role, BOTH already hold `DescribeImages`. → **no
   `demoPermissionsPolicy` edit, no role re-apply.** the OIDC-drift hazard does NOT apply here
   (no policy change occurs). the only remaining callout is for EXTERNAL callers on a
   hand-scoped ec2 policy (no `ReadOnlyAccess` / `AmazonEC2ReadOnlyAccess`) — they must add
   `ec2:DescribeImages` themselves; that stays a release note (per the wish's `.scope`).

3. **[decided by wisher — OUT of scope] belt-and-suspenders `rootDeviceName?` override** —
   the wish flags an optional explicit field on `DeclaredAwsEc2LaunchTemplate`
   (`template.rootDeviceName ?? described ?? throw`). **the wisher decided: NOT now — the
   override stays out of scope for this fix.** the `DescribeImages` lookup covers the stated
   acceptance; the override would add a domain-object field + cast changes + tests for a case
   no one has hit yet (`rule.prefer.wet-over-dry`). a clean, additive follow-up if ever wanted
   — no need for the end-of-road council. this fix ships the lookup alone.

4. **[answered — build-stone fork] error class for the absent-name throw** —
   `UnexpectedCodePathError` (wish default, file-symmetry) vs `ConstraintError` (a caller's
   bad `imageId`, exit-2). resolvable now via logic; the build stone picks. the vision defaults
   to the wish's `UnexpectedCodePathError`. see assumption #4.

## groundwork

### external research

- **`@aws-sdk/client-ec2` `DescribeImagesCommand`** — verified extant in the INSTALLED
  package (`node_modules/.pnpm/@aws-sdk+client-ec2@3.943.0/.../dist-types/commands/
  DescribeImagesCommand.d.ts`), and the `Image` model declares
  `RootDeviceName?: string | undefined` (`.../models/models_7.d.ts:2017`). response shape is
  `{ Images: Image[] }`. this is the same SDK package already imported in
  `setEc2LaunchTemplate.ts` and `getEc2LaunchTemplate.ts`, so the import is additive
  (`DescribeImagesCommand` alongside the extant `CreateLaunchTemplateCommand`, `EC2Client`).
  the ahbode live patch already proved this exact call returns `/dev/sda1` for a
  ubuntu-24.04 AMI. (no new dependency — declastruct-aws pins two client-ec2 versions,
  3.940.0 and 3.943.0, both carry the field.)

### internal research

- **`src/domain.operations/ec2LaunchTemplate/setEc2LaunchTemplate.ts:66`** — confirmed the
  hardcoded `DeviceName: '/dev/xvda'` inside `BlockDeviceMappings[0]`. the Ebs override
  (`VolumeSize`, `Encrypted`, `VolumeType: 'gp3'`, `DeleteOnTermination: true`) is correct
  and stays; only the `DeviceName` derivation changes.
- **fail-loud pattern** — this file already uses
  `UnexpectedCodePathError.throw('...', { ...context })` in four places (lines 33, 49, 102,
  114). the new absent-`RootDeviceName` throw mirrors these exactly — same class, same
  `{ imageId }`-in-context shape. (`helpful-errors` already imported.)
- **`getEc2LaunchTemplate.ts`** — the create path read-back is untouched; it already casts
  via `castIntoDeclaredAwsEc2LaunchTemplate`. `castIntoDeclaredAwsEc2LaunchTemplate` reads
  the block-device map back FROM AWS — worth checking in the build stone that the read-back
  does not assert `/dev/xvda` anywhere (it casts what AWS returns, so likely fine).
- **journey test `ec2LaunchTemplate.journey.integration.test.ts`** — currently uses ONE AMI
  (`ami-0c55b159cbfafe1f0`, Amazon Linux 2, real root `/dev/xvda`) across all cases.
  acceptance #5 requires adding a ubuntu AMI case so the device-name divergence is covered
  end to end. no unit test for `setEc2LaunchTemplate` is present yet — acceptance #5
  requires two new unit tests (faked `DescribeImages`), which will be the first for this
  operation.
- **`provision/aws.auth/resources.common.ts`** — `demoPermissionsPolicy` grants specific
  `ec2:*` actions (`RunInstances`, `StartInstances`, `ModifyInstanceAttribute`,
  `CreateNetworkInterface`, …) but **NO `ec2:Describe*` at all** — not even
  `DescribeLaunchTemplates` (which `getEc2LaunchTemplate` needs). this strongly implies the
  integration/journey tests run under the broader `ehmpathy-demo-sso` permission set, NOT
  the tightly-scoped `demoPermissionsPolicy`. so `ec2:DescribeImages` likely needs no change
  to the demo policy — but this must be confirmed (open question #2). the release-note
  callout for *external* hand-scoped callers stands regardless.

## what is awkward?

1. **an extra network read on a "build" operation.** `setEc2LaunchTemplate` now does an AWS
   read (`DescribeImages`) inside what reads like a pure setter. it's necessary — the real
   root name is only knowable from AWS — but it does add I/O and a failure mode to the
   create path. mitigated by placing it AFTER the findsert-return, so the idempotent path
   stays read-free.
2. **the fix is invisible in the domain object.** no field in `DeclaredAwsEc2LaunchTemplate`
   signals that the root device is AMI-derived — a reader of the domain object wouldn't know.
   the optional `rootDeviceName?` override (deferred) would make it visible but at the cost
   of a wider change. tension between explicitness and wet-over-dry; we lean wet.
3. **testing a value that comes from a live AMI.** the unit tests fake `DescribeImages`,
   which is correct, but the journey test needs a real ubuntu AMI id that stays valid in the
   test region — AMI ids are region-specific and rotate. the extant test already carries a
   stale-comment risk ("update for test region"); the new ubuntu case inherits it. a build
   concern, not a vision blocker.
4. **`/dev/xvda` still appears — as data, not a constant.** amazon-linux AMIs genuinely
   return `/dev/xvda`, so the string doesn't vanish; it just stops being hardcoded. a
   skim-reader might "fix" a test that expects `/dev/xvda` thinking it's the old bug. the
   ubuntu case + a comment should guard against that.
