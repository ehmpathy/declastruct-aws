### the integration failures found + FIXED here (buttonup, zero omissions)

the first `integration` run of the ec2LaunchTemplate journey came back **3 passed, 9 failed**. this
was a REAL defect this fix surfaced, not an inherited excuse:

- **root cause:** the journey (and the acceptance fixture) declared a **hardcoded** AMI id
  (`ami-0c55b159cbfafe1f0` in the journey, `ami-0453ec754f44f9a4a` in acceptance). before this fix,
  `CreateLaunchTemplate` stored any AMI id string WITHOUT validation, so a stale/deregistered id
  created a template fine. this fix adds a `DescribeImages` read to `setEc2LaunchTemplate`, which now
  correctly validates the AMI — surfacing that the journey's hardcoded id had gone stale
  (`InvalidAMIID.NotFound: The image id '[ami-0c55b159cbfafe1f0]' does not exist`).
- **fix (journey):** the amazon-linux cases now read the current AL2023 x86_64 AMI at run time via a
  `DescribeImages` owner+name filter (newest by `CreationDate`) — the same pattern case5 already used
  for ubuntu. no hardcoded id that rotates stale. re-run → **12 passed, 0 failed**.
- **fix (acceptance, consequence-fix):** the same hardcoded-AMI hazard sat in
  `resources.acceptance.ts` (`ami-0453ec754f44f9a4a`, used by both the NAT + ec2 launch templates).
  since this fix makes `setEc2LaunchTemplate` validate the AMI on apply, a stale acceptance id would
  404 the CI acceptance apply the same way. replaced the hardcoded const with a run-time
  `getAmazonLinux2023ImageId()` read (one `DescribeImages`, shared by both templates), so the
  acceptance suite is resilient to rotation. verified via types + lint + format + `npm run build`.

### acceptance — CI venue (reasoned, not a skip)

the fix's run-time behavior is proven against REAL AWS by the journey integration (12/12, incl. the
ubuntu `/dev/sda1` teeth read + the amazon-linux run-time lookup). the acceptance fixture was made
rotation-robust so this fix does not break the CI acceptance apply.

a full LOCAL acceptance apply is NOT run here, deliberately: the acceptance suite provisions the
entire declared stack (VPC + NAT + EC2 + IAM + Lambda + budgets + cost reports + SSM tunnels) against
the shared demo/test account. the repo's own hazard briefs (`rule.forbid.test-blocking-orphans`,
`rule.require.vpc-test-cleanup-both-ends`, `howto.unblock-resource-contention`) treat that as a
CI-run, contention- and orphan-prone, full-stack operation. running it ad hoc from a local worktree
risks exactly the orphans / VPC-cap contention those briefs forbid. CI is its proper venue and runs
it on the release; the fixture change + `npm run build` confirm the prod code + wish compile and the
AMI is read at run time.

### coverage gap found + FIXED at this gate (self-review r1)

the `has-behavior-coverage` self-review surfaced one vision behavior with no EXPLICIT test: the
idempotency-cheap property (vision timeline step + wish acceptance #4 edge) that a findsert of an
EXTANT template returns early and NEVER reaches the `DescribeImages` read (the read is
create-path-only). it was only implicitly covered by the journey idempotency case, which does not
assert the skip. a refactor that moved the read before the findsert-return would add a wasted
describe to every warm apply — a real perf + failure-surface regression on the idempotent path.

FIXED: added `setEc2LaunchTemplate.test.ts` case4 — mocks the unique lookup to find the extant
template, calls findsert, and asserts `DescribeImages` command-count == 0 AND
`CreateLaunchTemplate` command-count == 0 (the found template returns read-cheap). unit scope
25 → 26, full unit 985 → 986, all green.
