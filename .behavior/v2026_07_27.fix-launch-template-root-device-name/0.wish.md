# wish: fix — launch template must target the AMI's real root device, not a hardcoded name

## .what (one sentence)

`setEc2LaunchTemplate` hardcodes the root block device to `/dev/xvda` (amazon-linux's root
name); it must instead target the AMI's ACTUAL root device name, so the root-volume override
(encrypt / size / gp3) lands on the real root for ANY AMI family — not a phantom device on
images (e.g. ubuntu = `/dev/sda1`) that name their root differently.

## .source (authoritative)

the full write-up — observed vs expected, the two failure modes, the proof it works — was handed
off inline in the dispatch. treat the acceptance below as the contract of record:

- **repo:** `ehmpathy/declastruct-aws`
- **file:** `src/domain.operations/ec2LaunchTemplate/setEc2LaunchTemplate.ts` (line 66,
  `DeviceName: '/dev/xvda'`)
- **version affected:** 1.9.0 (current)

## .why

the `BlockDeviceMappings` entry exists to override the root volume — AWS matches that override
to a block device BY NAME, so the name MUST be the AMI's real root device, which is AMI-specific
(amazon-linux `/dev/xvda`, ubuntu `/dev/sda1`). with the name hardcoded, on a ubuntu AMI the
override targets a device the image lacks, and two things break:

1. **encrypted-root hibernation fails** — the real root launches UNencrypted from the AMI
   snapshot, so `RunInstances` with `HibernationOptions.Configured = true` is rejected with
   `UnsupportedHibernationConfiguration: For hibernation, the root device volume must be
   encrypted.`
2. **the size override is silently dropped** — the real root launches at the AMI's default size,
   not `rootVolumeSize`.

net: declastruct-aws@1.9.0 is effectively amazon-linux-only for an encrypted/sized root. this
surfaced on an ahbode grove-box AMI cutover from amazon-linux-2023 to ubuntu-24.04-LTS (box
declares `hibernation: true` + `rootVolumeEncrypted: true`): the template built cleanly but the
box's `RunInstances` died. it worked on AL2023 (device name matched), broke on ubuntu.

## .acceptance (what proves it done — authoritative)

1. **root device name is AMI-derived, not hardcoded** — for an AMI whose real root is
   `/dev/sda1`, the emitted `CreateLaunchTemplateCommand` input carries
   `BlockDeviceMappings[0].DeviceName = '/dev/sda1'`, NOT `/dev/xvda`. the value comes from the
   AMI's authoritative `DescribeImages(...).Images[0].RootDeviceName`.
2. **fail-loud when the lookup yields no name** — if `DescribeImages` returns an absent
   `RootDeviceName` for the template's `imageId`, the operation throws a named error (e.g.
   `UnexpectedCodePathError`) with the `imageId` in context — never a silent fallback to a guess.
3. **the root-volume override still lands** — the emitted entry still carries the encrypt / size
   (`rootVolumeSize`) / `gp3` / `DeleteOnTermination` override, now on the correct device.
4. additive + non-regressive — an amazon-linux AMI (root `/dev/xvda`) generates exactly as
   before; callers that already worked are unaffected.
5. **tests**:
   - unit — a faked `DescribeImages` returning `RootDeviceName: '/dev/sda1'` proves the command
     input carries `DeviceName: '/dev/sda1'` (RED before, GREEN after).
   - unit — a faked `DescribeImages` returning an absent `RootDeviceName` proves the named throw.
   - journey (`ec2LaunchTemplate.journey.integration.test.ts`) — a ubuntu AMI case alongside the
     amazon-linux one, so the device-name divergence is covered end to end.

## .the proposed shape (advisory — the mechanic owns the HOW)

the handoff sketches a precise diff: add `DescribeImagesCommand` to the `@aws-sdk/client-ec2`
import; after the immutable-upsert throw, `ec2.send(new DescribeImagesCommand({ ImageIds:
[template.imageId] }))`, read `Images?.[0]?.RootDeviceName`, throw the named error if absent;
then use that value for `DeviceName` in the block-device map. mirror the repo's extant emit +
error patterns rather than a literal copy of the sketch. the OUTCOME above (override lands on the
AMI's real root, fail-loud on an absent lookup, no regression) is the contract.

### optional belt-and-suspenders (advisory)

expose an explicit `rootDeviceName?: string` override on `DeclaredAwsEc2LaunchTemplate` and
prefer it over the looked-up value (`template.rootDeviceName ?? described ?? throw`). the lookup
covers the common case; the override is an escape hatch. treat as a scoped follow-up if it grows
the change.

## .scope

- primary: the root-device-name derivation in `setEc2LaunchTemplate.ts` (the `DescribeImages`
  lookup + its use in the block-device map + the fail-loud throw), plus the tests in acceptance #5.
- release note: `DescribeImages` is a new read the caller's role must hold — part of `ec2:*` and
  covered by `AmazonEC2ReadOnlyAccess`, but anyone on a hand-scoped ec2 policy must add
  `ec2:DescribeImages`. call this out in the release notes.
